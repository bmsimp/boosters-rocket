## Booster Rocket: rules for agents

Booster Rocket is an open-source, self-hosted parent portal for booster clubs: each family signs in and sees only its own students, what it owes and what it must sign, while staff manage the roster. QuickBooks Online holds the club's books and the roster; the portal reads them and keeps a cache, and writes one thing back: a parent's own phone and address (Writes to QuickBooks, below).

**Where the truth lives**
- `PRODUCT.md`: users, principles, terms, voice. `DESIGN.md` and `src/app/booster.css`: the visual system.
- `docs/superpowers/specs/2026-11-06-booster-rocket-v1-design.md`: the v1 spec. Later specs in that folder override the parts they name, and win where they disagree: `2026-11-10-parent-email-code-sign-in-design.md` (parents sign in with the portal's own emailed code, not Entra External ID), `2026-11-10-quickbooks-connection-and-roster-design.md`, `2026-11-11-parents-from-quickbooks-design.md`.
- `docs/superpowers/plans/2026-11-07-v1-roadmap.md`: what is built and what is next. Read it for current status.

**How work is done**
- One screen-sized slice at a time, from a short brief. Tests are written with the code. No long plans with code in them.
- Do the slice in the brief and nothing else. Say in your report what you left undone, and anything that surprised you.

### Privacy rules that are never traded
- The family comes only from the session: `ctx.familyQboId` from `requireParentPage()` or `parentAction`. An id from the URL, a form or an action argument is untrusted: look it up within that family, and answer `notFound()` or refuse when it isn't there.
- Staff-only query modules are never imported by parent code: `src/lib/roster/queries.ts` (`loadRosterPage`, `rosterEntry` load every family); in `src/lib/parents/directory.ts`, `listPeople`, `getPerson`, `heldReview`, `familySignins` (the note at the top of the file); and `src/lib/seasons/setup.ts`, `subjects.ts` and `staff-progress.ts`. They are `STAFF_ONLY_IMPORTS` in `tests/integration/page-guards.test.ts`. A parent page reads through a query that takes the family id and returns that family alone.
- A note staff write about a family is for staff: a waiver's reason is in the audit log and on staff pages, and a parent reads only "Waived". `seedTwoFamilies()` gives each family such a note (`season.staffOnly`), and `tests/integration/parent-isolation.test.ts` fails a parent page that shows one, even the family's own.
- Anything stored against a QuickBooks id means another customer in another company. It is deleted when a different company is connected, inside `clearRosterOfOtherCompanyLocked()` (`src/lib/roster/source.ts`): parent access, `family_money`, the seasons' ticks, waivers and chosen lists (`clearSeasonRecords()`), the item list and the money run's place (`clearMoneyRecords()`), every volunteer sign-up (`clearVolunteerRecords()`) and every signature request with its consents (`clearFormRecords()`). A new table keyed by a QuickBooks id is cleared there too.
- QuickBooks text (names, emails, memos) is rendered as text only: never `dangerouslySetInnerHTML`, never built into HTML, a URL or CSS.
- Pass a client component only what it shows: every prop is sent to the browser, rendered or not.
- Nothing family-specific is ever cached in a service worker or a shared cache. Route handlers that return data send `cache-control: no-store`. The one exception is the club's app icons (`src/app/icons/[name]/route.ts`): public, the same for everyone, and kept by their `?v=` version.
- The service worker (`public/sw.js`) stores one thing, `/offline.html`, and does one thing: it answers a page navigation that failed for lack of a connection with that page. It has one `cache.put`, no `add` or `addAll`, and no `respondWith` for anything but `mode === "navigate"`; it never stores a page, the data a page loads, an API answer or a script. Never add a caching strategy to it. `tests/unit/pwa-static.test.ts` reads the file for this, and `tests/e2e/pwa.spec.ts` signs a parent in, browses, and checks the caches hold `/offline.html` and nothing else. `public/offline.html` is the same for every club and person: no club name, no family data, no script.
- No secret reaches the browser: `scripts/check-client-bundle.mjs` searches the built client files for the secret values. Never read `process.env` or `@/env` in a client component.

### Checklists
New parent page (`src/app/(parent)/**/page.tsx`; example `src/app/(parent)/payments/page.tsx`):
- Make the first line of the page `const ctx = await requireParentPage("/its-address");`: the page's own address, written out as a string, so a visitor who has to sign in or choose a family first is brought back to it. A dynamic segment passes a template that starts with the fixed part: `` requireParentPage(`/forms/${id}`) ``. Only Home (`/`) calls it with no argument. `tests/integration/page-guards.test.ts` refuses a missing address, another page's, or one it can't read; `tests/integration/parent-isolation.test.ts` checks the redirect carries it.
- The parent layout is not a guard: it calls `parentLayoutCtx()` (`src/lib/guards.ts`), draws the frame for a signed-in parent and never redirects. Do not put `requireParentPage()` in a layout: its redirect runs before the page's and cannot name the page.
- The return path travels through the browser, so it is checked at every read by `safeReturnPath()` (`src/lib/auth/return-path.ts`): only a plain parent path on this site gets through, and anything else lands on `/`. Never redirect to a `next` value that has not been through it. A new top-level folder in `src/app` outside `(parent)` that holds a page or a route handler is added to `NOT_PARENT_SECTIONS` there (`tests/unit/return-path.test.ts` fails until it is).
- Read data with `ctx.familyQboId` only. Do not audit a parent viewing their own family.
- A page that gets a tab: add it to `PARENT_NAV` (`src/app/components/parent-nav.ts`; its icon goes in `parent-tabs.tsx`) and to the expected list in `tests/unit/parent-nav.test.ts`, and take it out of the 404 list in `tests/e2e/public-pages.spec.ts`.
- A query module for parent pages outside `src/app/(parent)/`: list it in `PARENT_CODE_ELSEWHERE` (a file) or `PARENT_FACING_LIB` (a folder) in `tests/integration/page-guards.test.ts`, so the staff-only import scan reads it.
- A dynamic segment: add its params to `PARAMS` in both `tests/integration/parent-isolation.test.ts` and `tests/e2e/parent-session.spec.ts` (there with ids from `scripts/seed-e2e.ts`). Each fails until it has them.
- New kinds of family data: seed them for both families in `seedTwoFamilies()` and add their strings to the markers.
- New `scripts/seed-e2e.ts` data for any family but `E2E-FAMILY`: add its strings to `OTHER_FAMILIES` in `tests/e2e/parent-session.spec.ts`, the only test that reads the props sent to client components.

New parent server action (example `src/app/(parent)/family/details/actions.ts`, with the work in `src/lib/parents/contact-edits.ts`):
- Put `"use server"` first, in a file under `src/app/(parent)/`; export only functions wrapped in `parentAction`.
- Check every argument's type and size: it comes from the browser, whatever the type says. Re-check every id against `ctx.familyQboId`. Better, take no id at all: the example reads only its own form fields, and the record comes from the session (`loadMyRecord(ctx)`).
- Write the audit row in the same transaction as the write. Return the result shape below.
- The automatic gates cover pages and ids in path segments, not this. A server action, and any lookup that takes an id or a value from the query string or a form, gets its own test that calls it as family A with family B's ids in every field and proves nothing of B comes back or changes (`tests/integration/contact-edits.test.ts`).

New staff page (`src/app/staff/(app)/**/page.tsx`; example `src/app/staff/(app)/roster/[id]/page.tsx`):
- Make the first line `const ctx = await requireStaffPage("Area.Object.Level");` with a permission from `src/lib/permissions/registry.ts`, written as a string.
- A page that shows one family's or one person's data writes an audit row before it shows anything (`roster.family.read`, `parent.read`, `season.progress.family.read`).
- A page that gets a menu entry: add it to the `nav` list in `src/app/staff/(app)/layout.tsx` behind `can(e, "<the page's permission>")`, and to `tests/integration/staff-menu.test.ts` and the list in `tests/e2e/staff-menu.spec.ts`. The staff bar wraps its links onto further rows (`.bar-rows` in `booster.css`); the parent bar never does.

New staff server action (example `src/app/staff/(app)/parents/actions.ts`, with the write in `src/lib/parents/people.ts`):
- Put `"use server"` first; export only `staffAction("Permission", ...)` functions. Check every argument (`NOT_FROM_PAGE` in the example).
- Do the write in `src/lib/`, in one `db.transaction`, with `writeAudit(entry, tx)` inside it (actor, permission, before, after, ip).
- Call `revalidatePath`, then return the result shape.

New route handler (`route.ts`; examples `src/app/api/internal/worker/route.ts`, `src/app/api/quickbooks/callback/route.ts`, and for a download a staff member asks for, `src/app/staff/(app)/audit/export/route.ts`):
- Prefer a page or a server action. A handler has no guard wrapper: check the session or token in the handler itself, first.
- Machine-facing endpoints live under `/api/`; anything else is redirected to `/setup` while setup is open (`src/proxy.ts`).
- List it in `ROUTE_HANDLERS` in `tests/integration/page-guards.test.ts` with how it is guarded and the test that proves it.

Rules for all of them:
- Audit: `writeAudit` in the same transaction as every write. A staff read of one family's or person's data is audited. A parent viewing their own family is not. Write the action as a string (`action: "area.thing.verb"`) and give it words in `ACTION_NAMES` (`src/lib/audit/actions.ts`), which the audit page and its export show: `tests/unit/audit-actions.test.ts` fails for an action with none.
- Permissions are in `src/lib/permissions/registry.ts`. `ADMIN_ONLY` ones can't be given to a custom role by any pattern (`tests/unit/permissions/rules.test.ts` tries every form); the audit log (`Audit.Log.Read`, its rows hold staff-only notes) and the Health page (`Admin.Health.Read`) are among them. A role takes any other permission by its exact name.
- Action result: `{ ok: true, message }` or `{ ok: false, errors }` (`errors` is a list of sentences to show). Client forms call actions through `safely()` from `src/app/components/action-error.ts`.
- A guard refusal says the same thing whatever the reason. Never tell a parent why, or that another family exists.

### Money
- Amounts are integer cents everywhere in the portal. `toCents()` converts a QuickBooks number once, where it comes in, and `formatMoney(cents, currency)` is the only formatter (`src/lib/money/cents.ts`). Never add or compare dollars, and never format an amount yourself. The currency is the invoice's own (`currencyOf`), USD when absent.
- A parent page shows money through `loadFamilyMoney(ctx.familyQboId)` (`src/lib/money/family-money.ts`) and the components in `src/app/(parent)/money-box.tsx`: `<MoneyBox ctx={ctx} />` on Home, `MoneySection` and `PaidSection` on Payments. Do not query invoices from a page. A page shows a family's money only when `loadMyFamily()` returns the family: Home and Payments ask it first, and show `NotSetUpBox` and no money when it returns null.
- `family_money` holds one row per family: the last successful read (invoices as shown, total, `BalanceWithJobs`, currency, company, time) and the last failed try. A page load shows a fresh row at once (`money.settings` `{ freshSeconds }`, default 300); otherwise it makes one live read with a short timeout, and on failure shows the last figures marked not current with Pay switched off. The total is the sum of the open invoices shown, not QuickBooks' balance.
- The note on figures that are not current is the same whatever the cause (an outage, a connection only an Admin can mend, another read under way): it never says QuickBooks is down and never promises when paying will be back (`DESIGN.md`, Money lines).
- Whose invoices: the family customer and its active direct sub-customers of the student or parent type (flat: the member alone), read from the roster cache for the session's family, and only for an active family. Nothing in a request selects a customer. An id goes into query text only after `isQboId()` (digits only).
- Each stored invoice names the customer it was raised on (`customerQboId`). A row that holds an invoice of a customer the cache no longer puts in the family (a student moved or made inactive) is treated as absent, however fresh (`mayShow`), and saving a membership shape deletes every row.
- `BalanceWithJobs` counts every customer under the family at every depth, so it is read and compared (the credit line, the `money.balance_mismatch` audit) only when the cache holds nothing under the family but the customers whose invoices make up the total (`balanceCoversTheSame`).
- Never the wrong company: no live read unless QuickBooks is connected to the company the roster cache came from, and a stored row from another company is treated as absent.
- A Pay button's address goes through `safePayLink()` (`src/lib/money/pay-link.ts`): https on `intuit.com` or a subdomain, or no button. Due dates are said in words by `DueLine` (`src/app/(parent)/due-line.tsx`) against the club's own date, which `loadFamilyMoney()` returns with the figures (`today`; see The club's date).
- QuickBooks reads for money go through the client's readers (`qboInvoices`, `qboCustomerById` in `src/lib/quickbooks/client.ts`), which only GET. The invoice query strings (`INVOICE_QUERIES`) have not been tried against a real company yet (roadmap, checks table): do not change them without trying the new string in the sandbox.
- Every query answer is read strictly (`strictRowsOf`), because an empty one is acted on: no invoices reads as "nothing owed", and no customers would empty the roster. Only a 200 whose `QueryResponse` is an object holding no rows means no rows. Any other 200 is refused (`bad_answer`, or `fault` for a Fault), never taken for an empty list. A new read does the same.
- A read made for a page load passes `failFast`. It never waits for the connection row lock: a token that is still good is read without it, and one that needs refreshing is refreshed once for all the page loads in the process, taking the row only if it is free (`busy` otherwise). Never call `accessToken()` from code a parent page runs: it waits its turn for that lock, through another caller's request to Intuit.

- Staff see money on Balances (`/staff/balances`, `Finance.Balance.Read`; each page audited before it shows anything). The worker's read of every family (`runMoneyJob()`, `src/lib/money/sweep.ts`; daily, or when staff ask) goes one family at a time, at most one request every 400 ms, into the same `family_money` rows by the same rules. It may wait for the connection row (parent page loads never do), keeps its place in the setting `money.run` and carries on at the next wake, and writes one audit row per run. Staff asking only record the ask (`askForMoneyRun()`); the worker starts it. The run also compares each customer's own `Customer.Balance` with its open invoices (`customer_checks`, "Worth a look" on Balances). `balances.ts`, `sweep.ts` and `items.ts` load every family: staff only (`STAFF_ONLY_IMPORTS`). The products and services a payment requirement picks from are `qbo_item`, read with `ITEM_QUERY` (not yet tried against a real company), emptied by `clearMoneyRecords()` on a change of company. A stored invoice carries `itemQboIds`; a row stored without them is read again, never guessed at.

### Writes to QuickBooks
- The portal sends QuickBooks one write: `qboUpdateCustomerContact()` in `src/lib/quickbooks/client.ts`, a sparse update of one customer's phone and billing address. Only `src/lib/parents/contact-edits.ts` may name it, and only `src/app/(parent)/family/details/actions.ts` may call that module's `saveMyContact()`. `tests/unit/quickbooks-writes.test.ts` holds all of it: no other request that isn't a GET but the token and revoke calls, no PUT, PATCH or DELETE, nothing written to the log. A new write is a decision named in a slice brief; it adds its function and its caller to that test's lists on purpose.
- The request's address, body and Fault codes are `CUSTOMER_UPDATE`, in one place, and have not been tried against a real company (roadmap, checks table). Change the body only together with the stub (`tests/helpers/qbo-stub.ts`), after trying it in the sandbox.
- Which record: the session's own, from `loadMyRecord(ctx)` (`src/lib/parents/my-family.ts`), found as `loadMyFamily()` finds `me`. Its id never reaches the browser, and nothing the browser sends names a customer. `MyContact.edits` (`"own"` or `"family"`) is what shows the "Update my details" link.
- Nothing is overwritten: the form carries the SyncToken it was shown, the save reads the record first, and a record that has moved on is answered with its current values (v1 spec §6.3). Only what changed is sent. Nothing is tried twice except after a 401; after a timeout or a 5xx the parent is told the portal can't tell whether it saved.
- Like a page load's reads, a save never waits for the connection row (`accessTokenForPage()`), refuses at once when only an Admin can mend the connection, and sends nothing unless QuickBooks is connected to the company the roster cache came from.
- Every save is audited with before and after in the transaction that updates the cached phone and SyncToken (`parent.contact.save`); a refused or failed one with its short code. Saves and opens of the edit page are rate-limited per parent (`RATE_LIMITS` in `src/lib/parents/rate-limit.ts`, pinned by `tests/integration/rate-limit.test.ts`).
- What the portal reads and changes in QuickBooks is said to staff in one set of words, `QUICKBOOKS_USE` (`src/lib/quickbooks/what-it-does.ts`), used by the QuickBooks settings page, its setup step and the Health page. A new read or write changes them there.
- The roster refresh believes an empty roster from one answer only: a well-formed one, and never over a cache of the same company that holds customers (`no_customers` in `src/lib/roster/refresh.ts`). QuickBooks never deletes a customer, and an empty roster ends every parent's access.

### Seasons
- A season has steps, a step has requirements, and progress is one `requirement_progress` row per requirement and family or student (a tick, a waiver with its reason, or both). The tables hold all four kinds: form, payment, volunteer, checklist.
- How a kind is met is one entry in `KIND_RULES` (`src/lib/seasons/kinds.ts`), the only place that knows. All four are built, so staff can create every kind: a checklist item is met by a staff tick ("Done", "Not done yet"); a form when Documenso says its document is COMPLETED (`formRule`, `src/lib/forms/kind.ts`: "Signed", "Not signed yet", "Waiting for the other guardian", "Signed, being finished", "Declined", and "Not ready yet" while it has no template); a payment when invoices carrying its QuickBooks item (`requirement.item_qbo_id`) exist for the family or student and none is open (`paymentStanding()`, `src/lib/money/payment-rule.ts`: "Paid", "Not paid yet ($X left to pay)", "No invoice yet"); volunteering when confirmed credit reaches the amount in shifts or hours (`volunteerStanding()`, `src/lib/volunteer/rules.ts`; nothing is confirmed until check-in is built, so it reads "0 of 2 shifts done, signed up for 1"). What a form points at is the jsonb `requirement.form` (the template's id, title and last-changed time, any or every guardian); a volunteer requirement points at nothing: shifts name it in `volunteer_shift_requirement`. The rules that turn standings into "done" (`src/lib/seasons/progress.ts`) are pure and unit-tested: a step is done when every required item that covers the family or student is met or waived.
- A parent page reads its season only through `loadMySeason(ctx, family.students)` (`src/lib/seasons/my-season.ts`). A requirement that covers nobody in the family is dropped there, title and all. The staff page for one family reads through the same `loadFamilyStanding()` (`recorded.ts`), so the two can't disagree.
- Parents read "set" (the ruler's word); staff read "step". States are words with an icon (`StateWords`, `src/app/components/state-words.tsx`): done, to do, waived.
- A step or requirement with any tick or waiver is refused removal until staff clear them. Kind and applies-to are fixed once a requirement is made.
- A staff write that names QuickBooks ids (a tick, a waiver, a chosen list) reads the roster inside its transaction after `lockRosterAs(tx, tag)` (`src/lib/seasons/roster-lock.ts`): it holds the roster lock, so no refresh or change of company runs between the check and the write, and it refuses when the page that sent the ids was shown another company's roster. The page carries `currentRosterTag()`, read before the roster.

### Forms (Documenso)
- Forms are signed in the club's own Documenso (v1 spec §9 as corrected by `docs/superpowers/specs/2026-11-15-documenso-verification.md`). `src/lib/documenso/client.ts` is its only client: server only, a timeout on every call, errors as short codes, nothing logged, no token in any message. Its address, API token and webhook secret are Forms settings (`/staff/settings/forms`, `Settings.Forms.ReadWrite`, Admin only), the secrets sealed; the address must be exactly the origin Documenso is configured with.
- One `signature_request` per form requirement and subject (family or student); its id is the document's `externalId`. Its state is what Documenso's API last said, never what a webhook said: not opened, waiting, signed (waiting for the sealed copy), complete (COMPLETED, the only state that meets it), declined. `readAndStore()` (`src/lib/forms/requests.ts`) is the only way a state changes; the page, the webhook (`/api/documenso/webhook`: secret checked in constant time before the body is read, the message only a hint) and the worker's `forms.check` job (each open request read more than 5 minutes ago; asks Documenso to seal again after 20 minutes) all go through it, and each change is audited.
- A parent finds a form only through `findMyForm(ctx, id)` and `loadMyForms()` (`src/lib/forms/my-forms.ts`): within `ctx.familyQboId` and the forms its current season asks for. Nothing is made in Documenso and no signing token is read until the signed-in guardian has agreed to the consent text of the current `CONSENT_VERSION` (`src/lib/forms/consent.ts`; `signature_consent` records who, when, the address and the version). The signing token is never stored: it is read from Documenso at each open and given only to the guardian whose recipient it is. The frame is embedded directly; its "completed" message only makes the page read the state again.
- A completed request sets `evidence_owed` for the slice that stores the sealed PDF and audit record. Opens are rate-limited (`form_open_parent`). Tests: `tests/helpers/documenso-stub.ts` (`startDocumensoStub()`, behaving as the verification found: a role left out stays a recipient until deleted, search by `externalId` matches substrings, both email settings recorded) and `tests/helpers/forms.ts` (`connectForms()`, `seedFormRequirement()`, `seedRequest()`, `seedConsent()`). The browser seed never sets forms up, so the e2e run can't reach a Documenso.

### Volunteering
- Events, shifts and sign-ups (`src/lib/volunteer/`; staff `Volunteer.Event.Read` and `Volunteer.Event.ReadWrite`). An event's date and a shift's times are the club's wall-clock time, read as instants in the club's zone only when needed (`clock.ts`); an end at or before the start is the next morning. The cancelling cut-off is the setting `volunteer.settings` (default 48 hours before the shift).
- A parent sees a shift's count of places filled and their own family's sign-ups, never who else filled a place: not on a page, in a prop, an email or a calendar file. Parent reads and writes go through `src/lib/volunteer/my-volunteer.ts` with `ctx.familyQboId`; a place is filled by the guardian ("me") or an active student of that family, checked again in the action. `src/lib/volunteer/setup.ts` (sign-up lists by name) is staff only.
- Signing up locks the shift row, counts, then inserts, holding the roster lock shared, so the last place goes to one person and no change of company runs in between. Emails (with an `.ics` attachment, by SMTP or Graph) go to the guardian who took the place, about their own sign-up only. Tests: `tests/helpers/volunteer.ts` (`seedEvent()`, `seedShift()`, `seedSignup()`).

### The club's date
- `clubToday()` (`src/lib/settings/club.ts`) is the one place that decides which day it is: the date in the club's own time zone (a Club setting, an IANA name, UTC until set). Step ranges, a requirement's due date and an invoice's due words all use it. Never the server's date (`new Date()` cut to a day) or the viewer's for anything a parent reads as due or past.
- A test that needs two different days at one instant sets the club's zone to `Pacific/Kiritimati` and `Pacific/Pago_Pago`, which never share a calendar day (`tests/integration/payments-page.test.ts`, `seasons-parent.test.ts`).

### Operations
- `scripts/backup.sh <folder>` writes a dump, checks it can be read back, keeps the newest 14 and records the time in the setting `backup.last_success`; `scripts/restore.sh <file> <database>` loads one beside the target and renames it in only when all of it loaded. `scripts/poc/deploy.sh` backs up before it migrates and stops if that fails. `tests/integration/backup-restore.test.ts` really dumps, restores and compares, through the database's container (or the machine's `pg_dump` and `psql` when `BR_DB_CONTAINER` is empty). Neither script prints a secret; new scripts join the shellcheck list in `.github/workflows/ci.yml`.
- A visitor's address is read in one place, `clientIpFrom()` (`src/lib/request.ts`), from the one header named by `CLIENT_IP_HEADER` (`src/env.ts`; default `cf-connecting-ip`, or `none`). Better Auth is never pointed at a header of its own: it reads the portal's stamp, written by `stampClientIp()` and `withClientIp()`. Never copy a Next.js request with `new Request(req)`: build it from its parts, as `withClientIp()` does. With no address (`none`, or a header the proxy doesn't send) the per-IP sign-in limits are skipped, since every visitor would share one count, and with `none` Better Auth is told so (`clientAddress()`, `src/lib/auth/client-address.ts`); the Health page's parent line says when the latest sign-ins have no address.
- The portal's address is `APP_URL`, set by whoever installs it. No host name is written into code, scripts or env examples: `scripts/poc/setup.sh` takes the address as its argument, and `deploy.sh` refuses an env file without one. The setup page and the Health page show the address and warn when the browser reached the portal under another (`PortalAddress`).
- The Health page (`/staff/health`, Admin only) is `healthReport()` in `src/lib/health/report.ts`: one line per part, in words, with when it last worked. It has lines for Documenso (`forms`) and for the daily read of every family's invoices (`money`). A new outside service or job adds its line there and its key to `tests/integration/health-page.test.ts` and `tests/e2e/ops.spec.ts`. `/api/health` stays a bare liveness check.
- The daily clean-up (`cleanUp()` in `src/lib/jobs/cleanup.ts`) deletes only rows strictly past their life. Every table is named once in `CLEANED_TABLES` or `KEPT_TABLES` (with why), and `tests/integration/cleanup.test.ts` fails for a table in neither. A new table whose rows expire gets its delete there, with a boundary test (a row one second inside its life stays).

### Database and migrations
- Conventions in `src/lib/db/schema.ts`: singular snake_case tables and columns; uuid primary keys with `defaultRandom()` for the portal's own records and `bigserial` for logs; `timestamp(..., { withTimezone: true })` with the `created()` and `updated()` helpers; enums as `text(..., { enum })`; QuickBooks ids as text in `*_qbo_id` columns; emails stored trimmed and lower-cased; sealed secrets as `*_ciphertext` plus `*_key_id`; indexes named `<table>_<what>_ix` and `_uq`; a comment above each table saying what it holds.
- Generate with `pnpm db:generate --name <snake_name>`. If drizzle-kit asks whether something was renamed, stop: split the change into an additive migration and a finishing one (see `0004_parents_additive`, `0005_parents_finish`).
- Never edit an applied migration: `0000` to `0009` are deployed, and `0010_family_money` to `0015_forms` (with `0013_staff_money` and `0014_volunteer`) are merged on `parent-portal`. New changes start at `0016`.
- Only one agent at a time may add migrations. In a parallel worktree, change `schema.ts` and generate a migration for your own test database, and say so in your report: migrations are regenerated when branches are merged.

### Tests
- Commands: `pnpm lint`, `pnpm typecheck`, `pnpm test` (vitest, unit and integration against a real Postgres), `pnpm vitest run <files>`, `pnpm e2e` (Playwright).
- The full suite runs its files in parallel: unit files beside integration files, each integration file on its worker's own database. `BR_TEST_WORKERS` sets how many workers (default half the cores, at most 6; any number from 1 to 16). `BR_TEST_WORKERS=1` runs the files one at a time on the run's database, as the suite once did. 158 files take about 2 minutes on this machine when it is quiet and up to 7 when it is fully loaded; one worker takes about 20. Still run it in the background and read its output, and never run two at once: a second run on the same database refuses to start. If a file you did not touch fails only with a timeout, run that file once on its own before you look further. While working, run the files you touched plus `tests/integration/invariants.test.ts`, `tests/integration/page-guards.test.ts` and `tests/integration/parent-isolation.test.ts`. Run the full suite before you finish.
- Postgres is the container `booster-rocket-db-1` on `127.0.0.1:5433` (user and password `booster`). The default test database is `booster_test`; the tests empty it again and again (`resetDb()` in `tests/helpers/db.ts`), so never point them at data you want.
- A private database: `docker exec booster-rocket-db-1 psql -U booster -d booster -c 'CREATE DATABASE "booster_<name>_test" OWNER booster'`, then `export TEST_DATABASE_URL=postgres://booster:booster@localhost:5433/booster_<name>_test`. The name must be short, lowercase letters, digits and underscores, ending in `_test`. Setting `DATABASE_URL` does nothing: vitest's config overrides it. Drop the database when you are done.
- Worker databases: worker 1 uses the run's database (`TEST_DATABASE_URL`). Worker N makes `<run>_w<N>_test` (for `booster_x_test`, `booster_x_w2_test` and so on) the first time it needs one, migrates it and marks it with a comment naming the run. The run drops them, and the scratch databases its tests made, when it ends. A run that is cut off leaves them; the next run on the same database uses them again or replaces them. A database with a worker's name that the run did not make is refused, never dropped. So never give a private database a name ending in `_w<N>_test`, and keep the name short: `_w16_migrate_parents_test` must still fit in 63 characters. When you drop your private database, also drop any `booster_<name>_w*_test` a cut-off run left (`docker exec booster-rocket-db-1 psql -U booster -d booster -c '\l booster_<name>_*'` lists them).
- A test file's database is `process.env.DATABASE_URL` (`tests/setup/worker.ts` sets it before the file loads). A script a test spawns gets it from `process.env`. A scratch database comes from `scratchDatabase(purpose)` in `tests/setup/database-url.ts`; a new purpose is added to `SCRATCH_PURPOSES`, so the run drops what its tests left. A unit test has no database (its `DATABASE_URL` names a port nothing listens on), so a test that needs Postgres goes in `tests/integration/`.
- Tests run beside each other on a shared machine. No fixed port (listen on 0), no file outside a `mkdtemp` folder, and no sleep that guesses how long other work takes. Wait for the thing itself: `stub.idle()` once the QuickBooks stub has answered everything, `untilALockIsAwaited()` (`tests/helpers/db.ts`) to prove one write waits for another, or poll `stub.apiCalls()`. A parallel run gives a test 20 s and a hook 30 s. Making or dropping a database waits for a checkpoint of the whole server, which has taken two minutes here, so a hook or test that does it passes a timeout of `300_000`.
- `resetDb()` deletes every row, then vacuums the tables the test wrote back to no pages, so rows read back in the order they were written. Never run VACUUM or change a table's storage in a test.
- A worktree: `git worktree add .worktrees/<name> -b <branch>`; inside it `pnpm install --frozen-lockfile --prefer-offline`; create a private database and export `TEST_DATABASE_URL` (vitest refuses the shared `booster_test` in a worktree, a database that is another run's worker database, and a run on a database another run is using). When its work is committed, remove it with `git worktree remove .worktrees/<name>`, and delete the folder if Windows leaves `node_modules` behind.
- e2e: export the env vars of the E2E step in `.github/workflows/ci.yml`, then `pnpm build`, `pnpm tsx scripts/seed-e2e.ts` (it migrates, empties the database, then seeds), `pnpm e2e` (about a minute and a half once built). That is the main tree: database `booster_test`, the app on port 3100, the mail sink on 2465.
- e2e in a worktree runs beside the others on its own database and ports. Export the same vars with `DATABASE_URL` naming the worktree's private database, plus `E2E_PORT=<port>`, `E2E_MAIL_PORT=<port>` and `APP_URL=http://localhost:<E2E_PORT>`: two ports no other tree uses (3101 to 3199 and 2466 to 2599). Seed and run with the same vars. The seed and `playwright.config.ts` refuse the shared `booster_test` in a worktree, and an `APP_URL` that is not the run's own address. Do not run `pnpm db:migrate` there: nothing checks its database.
- A vitest run on the same database wipes the e2e seed: seed again. Specs take addresses from `baseURL` and ports from `tests/e2e/run-config.ts`, never a number of their own. Both passes of a run (phone, then desktop) read one seed, so a spec leaves the seeded data as it found it, or passes from either state.
- Signed-in parent, vitest: `seedSignedInParent()` and `seedTwoFamilies()` in `tests/helpers/parent.ts` (also `seedParentIn()` for a family the test put in the cache itself, and `identityNow()` after changing a link); then import `tests/helpers/signed-in.ts` before anything from `src/` and call `asParent(identity)` (also `asParentChoosing`, `asRefusedParent`, `asStaff`, `asRefusedStaff`, `renderPage`, `pageOutcome`, `redirectOf`, `revalidatedPaths`). Example: `tests/integration/parent-helpers.test.ts`. When a helper lacks something, add it there with a small change; do not write a private mock block in a test file.
- The real session read (sign-in, renewal, the cookie): import `tests/helpers/page-request.ts` instead and call `fromBrowser(cookie)`. It replaces `next/headers` only, and cannot be imported into the same test file as `signed-in.ts`. Example: `tests/integration/parent-door.test.ts`.
- Money in tests: `seedTwoFamilies()` stores fresh figures for both families (`seedFamilyMoney()`, `moneyMarkers()`); their ids are not digits, so nothing is ever asked of QuickBooks for them. To read through the stub, use the families in `tests/helpers/money.ts` (`RIVERA`, `CHENOWETH`, with `connectCompany(stub)`, `stubInvoice()`, `ageMoney()`, `setFreshSeconds()`); `stub.oddInvoiceAnswer` makes the stub answer an invoice query with a 200 of any shape. A stored invoice must name a customer of its family (`customerQboId`), in `seedFamilyMoney()` and in `scripts/seed-e2e.ts`, or the row is not shown. A test file that renders a page showing money with QuickBooks connected mocks `@/lib/quickbooks/endpoints` onto the stub (top of `tests/integration/payments-page.test.ts`), so a read can never reach Intuit. `seedRosterRead()` (`tests/helpers/roster-cache.ts`) records a finished refresh and the company it read. A page test that depends on the due words sets the club's zone (The club's date); the fixtures' due dates are fixed, so never assert "soon" or "late" for them against the real clock.
- A parent's contact edits in tests: `tests/helpers/contact.ts` (`seedContactFamilies(stub)`, `contactForm()`, `customersOf()`, `shownTo()`, `inQuickBooks()`), with the money families, whose ids are digits. The stub answers the customer update as QuickBooks is understood to, and has switches for a refusal (`updateFault`), an edit made in QuickBooks at that moment (`beforeUpdate`), an answer that is lost (`loseUpdateAnswer`) and a server that can't be reached (`dropApi`). `stub.oddRosterAnswer` answers the roster's queries with a 200 of any shape; `stub.items` and `stub.oddItemAnswer` do the same for the item list.
- Seasons in tests: `seedSeason()` and `seedTwoFamilySeason()` in `tests/helpers/season.ts`. `seedTwoFamilies()` seeds a current season for both families, so Home for them has a ruler before `main` and requirement lines in the students box. It also gives each family a payment requirement (the trip deposit: paid for A, open for B), forms with a request in every state (`seedTwoFamilyForms()`) and a place on one shared volunteer shift (`seedTwoFamilyVolunteering()`), each with its markers.
- Signed-in parent, Playwright: `await context.addCookies([parentSessionCookie()])` from `tests/e2e/parent-session.ts` (Zelda, family `E2E-FAMILY`, seeded by `scripts/seed-e2e.ts`); staff: `staffSessionCookie()`.
- Fake QuickBooks with `startQboStub()` from `tests/helpers/qbo-stub.ts` and `vi.mock("@/lib/quickbooks/endpoints", ...)` (top of `tests/integration/roster-pages.test.ts`). Fake mail with `vi.mock("@/lib/mail/senders", ...)` and an outbox (`tests/integration/parent-door.test.ts`), or the real SMTP sink in `tests/helpers/mail-sink.ts`.
- No environment switch and no test-only branch under `src/`: tests replace modules from outside (`tests/unit/no-test-mail-path.test.ts`).

### Tripwire tests
A new feature will meet these. Changing one is a deliberate act named in the slice brief, never a fix made in passing:
- `tests/unit/quickbooks-writes.test.ts`: the portal's one write to QuickBooks, and who may send it (Writes to QuickBooks). It scans `src/lib/quickbooks`, `roster`, `jobs`, `money` and `src/lib/parents/contact-edits.ts`, and fails for a module that calls the client and is not scanned.
- `tests/integration/rate-limit.test.ts`: the whole of `RATE_LIMITS`. `tests/unit/audit-actions.test.ts`: every audit action written under `src/` has words. `tests/integration/staff-menu.test.ts`: who sees the Seasons, Progress, Balances, Volunteering, Forms and Health entries (Forms and Health to an Admin alone), and that one entry is current. `tests/e2e/staff-menu.spec.ts`: an Admin's whole menu stays inside the club bar at four widths (a new entry is added to its list).
- `tests/e2e/family-details.spec.ts`: the seeded parent records keep ids that are not digits (`E2E-P1`), so the browser run can never send one to Intuit.
- `tests/unit/parent-nav.test.ts`: the parent tabs are the pages that exist (Home, Forms, Payments, Volunteer, Family), each with a page on disk and an icon; `tests/e2e/parent-home.spec.ts` checks that the five fit a 360px phone. `tests/e2e/public-pages.spec.ts`: the list of pages that answer 404 until they are built (none is left but a made-up address).
- `tests/integration/cleanup.test.ts`: every table named once, cleaned or kept.
- `tests/integration/page-guards.test.ts`: the lists of pages outside the guarded trees, route handlers, staff-only imports and parent code outside `(parent)`; and the rule that a parent page passes its own address to its guard.
- `tests/unit/return-path.test.ts`: what `safeReturnPath()` refuses, and `NOT_PARENT_SECTIONS` against the folders of `src/app`.
- `tests/unit/pwa-static.test.ts`: what the service worker stores, the security headers in `next.config.ts`, the proxy's matcher, and the installed-app block being last in `booster.css`.
- `tests/e2e/parent-session.spec.ts`: `OTHER_FAMILIES`, with tests that fail when the seed gives another family a customer, an invoice, a requirement, a waiver or a volunteer sign-up the list would not find.
- `tests/e2e/quickbooks.spec.ts` and `tests/e2e/parents.spec.ts`: roster counts that follow from `scripts/seed-e2e.ts`; `tests/e2e/season.spec.ts`: the seeded season's step and requirement counts. Change the seed and the counts together.

### UI
- Use only the tokens and components in `DESIGN.md` and `src/app/booster.css`. No hex colors in components: the club's color is set at runtime.
- Font sizes in rem, never px. Tap targets at least 44px. Every status is words, plus an icon where there is room; color never carries meaning alone.
- Show an instant with `LocalTime` and a calendar date with `CalendarDate` (`src/app/components/`), not with your own formatting. Show an amount with `formatMoney()`.
- `src/app/booster.css` ends with five marked blocks: Home and Family, then Season (the ruler's heading, requirement lines, the staff season pages), then Volunteer, then Forms (the signing frame), then the installed app (safe areas, the install hint), which must stay last. `env(safe-area-inset-*)` for the top and sides appears only in that last block.
- Installed app: the manifest (`src/app/manifest.ts`) and the icons are built on each request from the club's settings and hold no hostname. Icon names are `ICONS` in `src/lib/pwa/icons.ts`. `InstallHint` and `RefreshOnResume` (`src/app/components/pwa/`) are given no club or family data.
- Copy follows the voice in `PRODUCT.md`: a warm, plain neighbor, kind about money. US English.
