## Booster Rocket: rules for agents

Booster Rocket is an open-source, self-hosted parent portal for booster clubs: each family signs in and sees only its own students, what it owes and what it must sign, while staff manage the roster. QuickBooks Online holds the club's books; the portal reads them and keeps a cache, which decides whose invoices a family sees. Families, students, guardians and sign-ins are the portal's own records, and it writes back to QuickBooks only what someone asks it to (`docs/agents/quickbooks-writes.md`).

**Where the truth lives**
- `PRODUCT.md`: users, principles, terms, voice. `DESIGN.md` and `src/app/booster.css`: the visual system.
- `docs/superpowers/specs/2026-11-06-booster-rocket-v1-design.md`: the v1 spec. Later specs in that folder override the parts they name, and win where they disagree: `2026-11-10-parent-email-code-sign-in-design.md` (parents sign in with the portal's own emailed code, not Entra External ID), `2026-11-10-quickbooks-connection-and-roster-design.md`, `2026-11-11-parents-from-quickbooks-design.md` (step 5 changes its "What staff cannot do here": staff now create, rename, move and make inactive in QuickBooks from the roster pages), `2026-11-15-documenso-verification.md` (forms). `2026-11-18-app-owned-families-design.md` is approved and being built in stages (the roadmap says which have shipped): the app is to own families, students, guardians and sign-ins, with the accounting system linked through a mapping screen. Until a stage ships, the rules below describe the code as it is; the slice that changes the code changes the rule in the same commit.
- `docs/superpowers/plans/2026-11-07-v1-roadmap.md`: what is built and what is next. Read it for current status.
- `docs/conformance.md`: the v1 spec requirement by requirement, as overridden, each with its state and the file and test that prove it (step 7). A change that builds, changes or drops a requirement changes its row. `docs/walkthrough.md`: every journey walked in a browser at 390 and 1440 wide, with what was found. `docs/runbooks/before-the-first-family.md`: every check only a person can make, in the owner's order; a check that code can now make leaves it.

**How work is done**
- One screen-sized slice at a time, from a short brief. Tests are written with the code. No long plans with code in them.
- Do the slice in the brief and nothing else. Say in your report what you left undone, and anything that surprised you.

### Privacy rules that are never traded
- The family comes only from the session: `ctx.familyId` (the app's own family record, `AppFamilyId`, which the session stores as that record's id, `parent_auth_session.family_id`) from `requireParentPage()` or `parentAction`. An id from the URL, a form or an action argument is untrusted: look it up within that family, and answer `notFound()` or refuse when it isn't there. A student's id is the app's, the same in every family: a lookup by a student's id is always joined to the family (`studentsStillIn()`).
- Staff-only query modules are never imported by parent code: `src/lib/roster/queries.ts` (`loadRosterPage`, `rosterFamilies`, `rosterEntry` load every family); in `src/lib/parents/directory.ts`, `listPeople`, `getPerson`, `familySignins`, `personContact`, `familyContact` (the note at the top of the file); `src/lib/seasons/setup.ts`, `subjects.ts`, `staff-progress.ts`, `due-reminders.ts` and `everyone.ts` (the season's reads for every family at once: every chosen list, tick and waiver; the parent-safe reads in `recorded.ts`, `season-rows.ts` and `src/lib/families/links.ts` each take the families and students they are for, and `src/lib/families/session-family.ts` the one family it is asked about); every module of `src/lib/signed-forms/` (the matrix, evidence, reminders, start again: they read many families); `src/lib/volunteer/setup.ts`, `staff-credit.ts`, `reminders.ts` and `moved-student.ts`; `src/lib/buyouts/staff.ts`, `daily-check.ts`, `setup.ts`, `moved.ts` and `close.ts`; `src/lib/staff-home/today.ts` (the staff home's counts); `src/lib/roster/writes.ts` and `queue.ts`; `src/lib/quickbooks/sandbox-check/run.ts` and `writes.ts`; and `src/lib/families/roster-import.ts` (the import of the app's own records from the roster, `docs/agents/app-records.md`); and `src/lib/roster/no-family.ts` (the customers no family is linked to, and "Create a family from this": it reads every customer of the roster cache); and `src/lib/parents/guardians.ts` (staff add, remove and reinstate guardians: it gives any address a sign-in for any family); and `src/lib/parents/people.ts` (staff block and rename people: a rename starts sends to QuickBooks, stage 3's slice 9h); and `src/lib/parents/contact-take-in.ts` (the take-in of contact details, stage 3's slice 11a: it reads every person, guardian row, family and cached customer); and `src/lib/accounting/mapping.ts` (the accounting links screen, stage 4's slice M1: it reads every family's guardians' sign-in addresses and every customer of the roster cache); and `src/lib/accounting/link-writes.ts` (its presses, stage 4's slice M3a: they link any family to any customer, reading every family's guardians and every customer of the roster cache to check it). `src/lib/parents/contact-queue.ts` (stage 3's slice 11b: a parent's change of their details queued in the save's transaction, and since slice S11e their confirmed change of sign-in email in the confirm's) is parent code, in `PARENT_CODE_ELSEWHERE`, and imports none of them, nor the QuickBooks client. They are `STAFF_ONLY_IMPORTS` in `tests/integration/page-guards.test.ts`. A parent page reads through a query that takes the family id and returns that family alone.
- A note staff write about a family is for staff: a waiver's reason is in the audit log and on staff pages, and a parent reads only "Waived"; a volunteer credit's note or a removed check-in's reason likewise (a parent reads "Added by the club"), and a form's start-again reason is only in its audit row. `seedTwoFamilies()` gives each family such a note (`season.staffOnly`), and `tests/integration/parent-isolation.test.ts` fails a parent page that shows one, even the family's own.
- Anything stored against a QuickBooks id means another customer in another company. From stage 2 of the app-owned families spec until stage 4 ships, a different company is refused (open question 18): connecting one (`completeConnect()`, `src/lib/quickbooks/connection.ts`, reason `roster_company`, in words on the QuickBooks setup page) and reading one's roster over this one's (`refreshRoster()`, a failed run `roster_company` that says to disconnect and connect the roster's company, asking QuickBooks nothing; its entry is in `docs/runbooks/health-warnings.md`) both stop while the roster cache names another company; reconnecting the same company works as before. The clear a change of company would run, and what it keeps, is in `docs/agents/app-records.md` ("A change of company"). A new table keyed by a QuickBooks id is cleared there too.
- QuickBooks text (names, emails, memos) is rendered as text only: never `dangerouslySetInnerHTML`, never built into HTML, a URL or CSS.
- Pass a client component only what it shows: every prop is sent to the browser, rendered or not.
- Nothing family-specific is ever cached in a service worker or a shared cache. Route handlers that return data send `cache-control: no-store` (the signed-form downloads too, with a fixed file name: QuickBooks text never goes into a header). The one exception is the club's app icons (`src/app/icons/[name]/route.ts`): public, the same for everyone, and kept by their `?v=` version.
- The service worker (`public/sw.js`) stores one thing, `/offline.html`, and does one thing: it answers a page navigation that failed for lack of a connection with that page. It has one `cache.put`, no `add` or `addAll`, and no `respondWith` for anything but `mode === "navigate"`; it never stores a page, the data a page loads, an API answer or a script. Never add a caching strategy to it. `tests/unit/pwa-static.test.ts` reads the file for this, and `tests/e2e/pwa.spec.ts` signs a parent in, browses, and checks the caches hold `/offline.html` and nothing else. `public/offline.html` is the same for every club and person: no club name, no family data, no script.
- No secret reaches the browser: `scripts/check-client-bundle.mjs` searches the built client files for the secret values. Never read `process.env` or `@/env` in a client component.

### Checklists
New parent page (`src/app/(parent)/**/page.tsx`; example `src/app/(parent)/payments/page.tsx`):
- Make the first line of the page `const ctx = await requireParentPage("/its-address");`: the page's own address, written out as a string, so a visitor who has to sign in or choose a family first is brought back to it. A dynamic segment passes a template that starts with the fixed part: `` requireParentPage(`/forms/${id}`) ``. Only Home (`/`) calls it with no argument. `tests/integration/page-guards.test.ts` refuses a missing address, another page's, or one it can't read; `tests/integration/parent-isolation.test.ts` checks the redirect carries it.
- The parent layout is not a guard: it calls `parentLayoutCtx()` (`src/lib/guards.ts`), draws the frame for a signed-in parent and never redirects. Do not put `requireParentPage()` in a layout: its redirect runs before the page's and cannot name the page.
- The return path travels through the browser, so it is checked at every read by `safeReturnPath()` (`src/lib/auth/return-path.ts`): only a plain parent path on this site gets through, and anything else lands on `/`. Never redirect to a `next` value that has not been through it. A new top-level folder in `src/app` outside `(parent)` that holds a page or a route handler is added to `NOT_PARENT_SECTIONS` there (`tests/unit/return-path.test.ts` fails until it is).
- Read data with `ctx.familyId` only. Do not audit a parent viewing their own family.
- A page that gets a tab: add it to `PARENT_NAV` (`src/app/components/parent-nav.ts`; its icon goes in `parent-tabs.tsx`) and to the expected list in `tests/unit/parent-nav.test.ts`, and take it out of the 404 list in `tests/e2e/public-pages.spec.ts`.
- A query module for parent pages outside `src/app/(parent)/`: list it in `PARENT_CODE_ELSEWHERE` (a file) or `PARENT_FACING_LIB` (a folder) in `tests/integration/page-guards.test.ts`, so the staff-only import scan reads it.
- A dynamic segment: add its params to `PARAMS` in both `tests/integration/parent-isolation.test.ts` and `tests/e2e/parent-params.ts` (there with ids from `scripts/seed-e2e.ts`; `parent-session.spec.ts` and `parent-a11y.spec.ts` both read it). Each fails until it has them.
- New kinds of family data: seed them for both families in `seedTwoFamilies()` and add their strings to the markers.
- New `scripts/seed-e2e.ts` data for any family but `E2E-FAMILY`: add its strings to `OTHER_FAMILIES` in `tests/e2e/parent-session.spec.ts`, the only test that reads the props sent to client components.

New parent server action (example `src/app/(parent)/family/details/actions.ts`, with the work in `src/lib/parents/contact-edits.ts`):
- Put `"use server"` first, in a file under `src/app/(parent)/`; export only functions wrapped in `parentAction`.
- Check every argument's type and size: it comes from the browser, whatever the type says. Re-check every id against `ctx.familyId`. Better, take no id at all: the example reads only its own form fields, and whose details it changes comes from the session (`ctx.parentId`, or `ctx.familyId` in books with no parent type: `readMyDetails()`).
- Write the audit row in the same transaction as the write. Return the result shape below.
- The automatic gates cover pages and ids in path segments, not this. A server action, and any lookup that takes an id or a value from the query string or a form, gets its own test that calls it as family A with family B's ids in every field and proves nothing of B comes back or changes (`tests/integration/contact-edits.test.ts`).

New staff page (`src/app/staff/(app)/**/page.tsx`; example `src/app/staff/(app)/roster/[id]/page.tsx`):
- Make the first line `const ctx = await requireStaffPage("Area.Object.Level");` with a permission from `src/lib/permissions/registry.ts`, written as a string.
- A page that shows one family's or one person's data writes an audit row before it shows anything (`roster.family.read`, `parent.read`, `season.progress.family.read`).
- A page about one family takes the app's own family id in its address (stage 3 of the app-owned families spec; the example and its buy-outs page, `/staff/balances/[familyId]`, `/staff/seasons/progress/family/[familyId]`, `/staff/volunteer/credit/[familyId]`): `familyRecordAt()` (`src/lib/families/address.ts`) first, so anything that isn't a family record's uuid (a QuickBooks id, a student's id, an unknown one) answers `notFound()` before any other query and before the audit row, which names the app's family (`family`). Its area's lookup takes that `AppFamilyId` and finds the family's customer once, through its own link, where the page still needs it. Every link to such a page is built by `src/app/staff/(app)/family-pages.ts` from an `AppFamilyId`, never from a QuickBooks id; a list finds its rows' records in one lookup (`linksOfCustomers()`, the family kind), and a row with none links nowhere.
- A page that gets a menu entry: add it to its group in `staffMenu()` (`src/app/staff/(app)/staff-menu.ts`: Home, Families, Season, Money, Settings as one entry, Admin) with the page's permission, to `tests/integration/staff-menu.test.ts`, and to `GROUPS` in `tests/e2e/staff-menu.spec.ts`. A new settings page is a section in `SETTINGS_SECTIONS` (`src/app/staff/(app)/settings/sections.ts`, and `tests/unit/settings-sections.test.ts`) instead of a menu entry: a plain view of what is set, its steps on their own page, starting with `<BackToSettings />`. The staff bar wraps onto further rows if it must (`.bar-rows` in `booster.css`); the parent bar never does.
- Build the page from the staff primitives: `DataTable` (`src/app/components/data-table.tsx`) for a list of like things, `Notice` and `ActionOutcome` (`src/app/components/notice.tsx`) for every state and every action's answer, and the form controls in `booster.css` (`.field`, `.checks`, `ChoiceGroup`). No bare status paragraph.

New staff server action (example `src/app/staff/(app)/parents/actions.ts`, with the write in `src/lib/parents/people.ts`):

- Do the write in `src/lib/`, in one `db.transaction`, with `writeAudit(entry, tx)` inside it (actor, permission, before, after, ip).
- Call `revalidatePath`, then return the result shape.

New route handler (`route.ts`; examples `src/app/api/internal/worker/route.ts`, `src/app/api/quickbooks/callback/route.ts`, and for a download a staff member asks for, `src/app/staff/(app)/audit/export/route.ts`):
- Prefer a page or a server action. A handler has no guard wrapper: check the session or token in the handler itself, first.
- Machine-facing endpoints live under `/api/`; anything else is redirected to `/setup` while setup is open (`src/proxy.ts`).
- List it in `ROUTE_HANDLERS` in `tests/integration/page-guards.test.ts` with how it is guarded and the test that proves it.

Page or action before sign-in (no session at all; example `src/app/sign-in/set-up/[token]/page.tsx` with `src/app/sign-in/password-link-page.tsx`, its action `src/app/sign-in/password-actions.ts`, the work in `src/lib/parents/password-set.ts`):
- It lives under `src/app/sign-in/`, already in `NOT_PARENT_SECTIONS`, never in a new top-level folder. List each page in `OTHER_PAGES` (`tests/integration/page-guards.test.ts`) with how it is protected and the test that proves it, in `BEFORE_SIGN_IN` of `tests/e2e/parent-a11y.spec.ts` (a target with what it needs, such as a live link: `Target.link`) and in `PUBLIC` of `tests/e2e/public-pages.spec.ts`; and render it in invariant 4 of `tests/integration/doors.test.ts` against `seedTwoFamilies()`, for a refused visitor and for a live one (a link minted for family A's parent). `parent-a11y.spec.ts` and `doors.test.ts` read the pages under `src/app/sign-in` from disk and fail for one missing from `BEFORE_SIGN_IN` or from `PUBLIC` (a link's page: `LINK_PAGES`). Everything under `src/app/sign-in` is scanned as parent code by `tests/integration/page-guards.test.ts`, so it imports nothing staff-only; a module of `src/lib` its pages or action run joins `PARENT_CODE_ELSEWHERE` there (`signin-links.ts`, `password-set.ts`).
- Its guard is what it is given (a link's token): one function decides whether it may be used (`linkVerdict()`, `src/lib/parents/signin-links.ts`), and the page and the action both go through it. Opening the page changes nothing (a mail scanner opens links too): no row, no count, no audit row, no mark. Only the form's submit acts.
- The action is `"use server"` in `src/app/sign-in/password-actions.ts` only, exporting only `beforeSignInAction` functions (`src/lib/guards.ts`, the door `"before-sign-in"`, which `tests/integration/invariants.test.ts` allows in that one file: another file is a decision named in a brief). Check every argument's type and size, and refuse anything else as a bad request.
- Every refusal gets one answer, the same words, and as near as possible the same reads and time, whatever the reason (unknown, used, expired, blocked, no row that counts, sign-ins off, over a limit: an over-limit refusal still reads the link and throws the answer away; it differs in being audited once per full window and with no person, and, when the address is over its limit, in counting nothing for the link); the reason goes only in its audit row. Limit it per IP address first (skipped when the address is unknown, as `takeIpLimit()` in `signin-codes.ts`) and then per token, counted under the token's keyed hash, never the token. Do slow outside work (the breach check) and the password hash outside any transaction, then check again under the person's lock and write, with the audit row, in one transaction.
- The page is `export const dynamic = "force-dynamic"`, so it is sent `no-store`; a page whose address carries a token is sent `Referrer-Policy: no-referrer` as a header, by its own rule in `next.config.ts` after the site's (`LINK_PAGES` there; `tests/unit/pwa-static.test.ts` pins it), so not even the head's first requests carry the token, and also sets `referrer: "no-referrer"` in its metadata (streamed into the body, since the root layout's metadata is async), and loads nothing from outside. It shows nothing about a person or a family (no name, no address, no username for a password manager), and its client form is given only what is already in its address.

Rules for all of them:
- A staff member acting on their own record only (their name) uses `staffSelfAction` (`src/lib/guards.ts`): no permission, and the action takes no id, only `ctx.staffUserId`.
- Audit: the audit page's record filter, and how it finds a record's rows written before an area moved to the app's ids, is in `docs/agents/audit.md`.
- Audit: `writeAudit` in the same transaction as every write. A staff read of one family's or person's data is audited. A parent viewing their own family is not. Write the action as a string (`action: "area.thing.verb"`) and give it words in `ACTION_NAMES` (`src/lib/audit/actions.ts`), which the audit page and its export show: `tests/unit/audit-actions.test.ts` fails for an action with none.
- Permissions are in `src/lib/permissions/registry.ts`. `ADMIN_ONLY` ones can't be given to a custom role by any pattern (`tests/unit/permissions/rules.test.ts` tries every form); the audit log (`Audit.Log.Read`, its rows hold staff-only notes) and the Health page (`Admin.Health.Read`) are among them. A role takes any other permission by its exact name. Every permission has plain words in `PERMISSION_WORDS` and an area in `PERMISSION_AREAS` (`src/lib/permissions/words.ts`; `tests/unit/permission-words.test.ts` fails without them). Roles are edited as a checklist and saved as exact names (`rulesFromChecklist()`, which adds the "see" permission a "change" one brings: `readTwinOf()`, Roster.Read for `Roster.Family.ReadWrite` and for `Accounting.Link.ReadWrite`); the linking permission ("Link families to accounting", open question 1 of the app-owned families spec) is not Admin-only: an Admin holds it and a custom role such as a treasurer's may be given it; a role written with patterns is shown with what it grants today, plus what a save would add, said in a note.
- Action result: `{ ok: true, message }` or `{ ok: false, errors }` (`errors` is a list of sentences to show). Client forms call actions through `safely()` from `src/app/components/action-error.ts`.
- A guard refusal says the same thing whatever the reason. Never tell a parent why, or that another family exists.

### Tests

- Commands: `pnpm lint`, `pnpm typecheck`, `pnpm test` (vitest, unit and integration against a real Postgres), `pnpm vitest run <files>`, `pnpm e2e` (Playwright). CI (`.github/workflows/ci.yml`) runs on pull requests and by hand, never on a push to `main`: on GitHub's hosted runners, or on the runner the repository variable `CI_RUNNER_LABELS` names (a JSON list of its labels; this repository's is `["self-hosted","br-ci"]`). Dependabot's pull requests always run on hosted runners, whatever the variable says (`runs-on` in both workflows): they bring third-party code, and a job on the club's runner can reach a privileged Docker daemon.
- The full suite runs its files in parallel: unit files beside integration files, each integration file on its worker's own database. `BR_TEST_WORKERS` sets how many workers (default half the cores, at most 6; any number from 1 to 16). `BR_TEST_WORKERS=1` runs the files one at a time on the run's database, as the suite once did. About 200 files take 5 minutes on this machine when it is quiet and up to 30 when other agents are testing. Still run it in the background and read its output, and never run two at once: a second run on the same database refuses to start. If a file you did not touch fails only with a timeout, run that file once on its own before you look further. While working, run the files you touched plus `tests/integration/invariants.test.ts`, `tests/integration/page-guards.test.ts` and `tests/integration/parent-isolation.test.ts`. Run the full suite before you finish.
- Postgres is the container `booster-rocket-db-1` on `127.0.0.1:5433` (Postgres 18; user and password `booster`). The default test database is `booster_test`; the tests empty it again and again (`resetDb()` in `tests/helpers/db.ts`), so never point them at data you want.
- Moving the local database to Postgres 18: after pulling the change that moved it, `docker compose up -d` leaves the database stopped, and `docker compose logs db` says why. Stop every test run on this machine first (the move stops the database they share), then from the main tree run `scripts/move-postgres.sh dev ~/booster-rocket-moving-to-postgres-18` and `docker compose up -d`. The database `booster` is kept, every row checked; the test databases are not carried (`booster_test` comes back empty from `docker/initdb`; make private ones again). The old data stays in the volume `booster-rocket_pgdata`: going back is `scripts/move-postgres.sh dev --stop`, checking out an older commit and `docker compose up -d`; coming forward again is the move with `--again` (it backs up what 18 holds into the folder first, and asks for `--discard-18` when 18 holds work done since the move). The dev move refuses in a checkout that has `deploy/.env` or `.env.poc`. Remove it only when sure: `docker compose down` (never `-v`), then `docker volume rm booster-rocket_pgdata`.
- A private database: `docker exec booster-rocket-db-1 psql -U booster -d booster -c 'CREATE DATABASE "booster_<name>_test" OWNER booster'`, then `export TEST_DATABASE_URL=postgres://booster:booster@localhost:5433/booster_<name>_test`. The name must be short, lowercase letters, digits and underscores, ending in `_test`. Setting `DATABASE_URL` does nothing: vitest's config overrides it. Drop the database when you are done.
- A worktree: `git worktree add .worktrees/<name> -b <branch>`; inside it `pnpm install --frozen-lockfile --prefer-offline`; create a private database and export `TEST_DATABASE_URL` (vitest refuses the shared `booster_test` in a worktree, a database that is another run's worker database, and a run on a database another run is using). When its work is committed, remove it with `git worktree remove .worktrees/<name>`, and delete the folder if Windows leaves `node_modules` behind.
- No environment switch and no test-only branch under `src/`: tests replace modules from outside (`tests/unit/no-test-mail-path.test.ts`).

### UI
- Use only the tokens and components in `DESIGN.md` and `src/app/booster.css`. No hex colors in components: the club's color is set at runtime.
