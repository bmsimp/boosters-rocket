# Testing in depth

What this covers: the test helpers and runs beyond the commands and database facts in `AGENTS.md` (Tests). The rules of `AGENTS.md` still apply.

## Tests, in depth

- Worker databases: worker 1 uses the run's database (`TEST_DATABASE_URL`). Worker N makes `<run>_w<N>_test` (for `booster_x_test`, `booster_x_w2_test` and so on) the first time it needs one, migrates it and marks it with a comment naming the run. The run drops them, and the scratch databases its tests made, when it ends. A run that is cut off leaves them; the next run on the same database uses them again or replaces them. A database with a worker's name that the run did not make is refused, never dropped. So never give a private database a name ending in `_w<N>_test`, and keep the name short: `_w16_migrate_guardian_test` (the longest scratch purpose) must still fit in 63 characters. When you drop your private database, also drop any `booster_<name>_w*_test` a cut-off run left (`docker exec booster-rocket-db-1 psql -U booster -d booster -c '\l booster_<name>_*'` lists them).
- A test file's database is `process.env.DATABASE_URL` (`tests/setup/worker.ts` sets it before the file loads). A script a test spawns gets it from `process.env`. A scratch database's name comes from `scratchDatabase(purpose)` in `tests/setup/database-url.ts` (a new purpose is added to `SCRATCH_PURPOSES`); make it with `makeScratchDatabase(purpose)` and drop it with `dropScratchDatabase(name)` (`tests/setup/worker-databases.ts`), which mark it with its run's comment as worker databases are. The teardown drops only the scratch databases its run marked (with their worker databases), and names in its output any of a scratch name it left alone, with the worker databases marked as that one's run: it may be another run's database, in use. A unit test has no database (its `DATABASE_URL` names a port nothing listens on), so a test that needs Postgres goes in `tests/integration/`.
- Tests run beside each other on a shared machine. No fixed port (listen on 0), no file outside a `mkdtemp` folder, and no sleep that guesses how long other work takes. Wait for the thing itself: `stub.idle()` once the QuickBooks stub has answered everything, `untilALockIsAwaited()` (`tests/helpers/db.ts`) to prove one write waits for another, or poll `stub.apiCalls()`. A request still waiting in the QuickBooks or Documenso stub when it is reset is dropped unanswered after its wait, so it never reaches the next test's switches, records or calls. A parallel run gives a test 20 s and a hook 30 s. Making or dropping a database waits for a checkpoint of the whole server, which has taken two minutes here, so a hook or test that does it passes a timeout of `300_000`.
- `resetDb()` deletes every row, then vacuums the tables the test wrote back to no pages, so rows read back in the order they were written. Never run VACUUM or change a table's storage in a test.
- e2e: export the env vars of the E2E step in `.github/workflows/ci.yml`, then `pnpm build`, `pnpm tsx scripts/seed-e2e.ts` (it migrates, empties the database, then seeds), `pnpm e2e` (about eight minutes once built). That is the main tree: database `booster_test`, the app on port 3100, the mail sink on 2465.
- The journeys: `tests/e2e/journey-parent.spec.ts` (a parent's whole visit, from the password and the emailed code to signing out) and `journey-staff.spec.ts` (a staff member's session, from the staff home to Settings), built from `tests/e2e/journey-helpers.ts` (`codeFor`, `staffMenuTo`, and `shot`, which writes pictures only when `WALK_SHOTS` names a folder outside the repository). They walk by taps, and the staff one removes what it made before and after. Signing a form in the real frame is `scripts/walk-forms-by-hand-local-documenso.ts`, run by hand against the local Documenso (`docs/walkthrough.md` says how; it reads the account file at run time and refuses any database but the tree's browser one); no suite runs it.
- e2e in a worktree runs beside the others on its own database and ports. Export the same vars with `DATABASE_URL` naming the worktree's private database, plus `E2E_PORT=<port>`, `E2E_MAIL_PORT=<port>` and `APP_URL=http://localhost:<E2E_PORT>`: two ports no other tree uses (3101 to 3199 and 2466 to 2599). Seed and run with the same vars. The seed and `playwright.config.ts` refuse the shared `booster_test` in a worktree, and an `APP_URL` that is not the run's own address. Do not run `pnpm db:migrate` there: nothing checks its database.
- A vitest run on the same database wipes the e2e seed: seed again. Migration 0041 refuses while a rename of a family, member or student or a student's create of the roster's company is waiting or stuck on the queue, and the browser seed leaves one there (a student's create): a local test or browser database seeded by a build before 0041 is cleared first (`docker exec booster-rocket-db-1 psql -U booster -d <database> -c 'DELETE FROM write_queue'`, a test database only) before the first test run or seed after it. Specs take addresses from `baseURL` and ports from `tests/e2e/run-config.ts`, never a number of their own. Both passes of a run (phone, then desktop) read one seed, so a spec leaves the seeded data as it found it, or passes from either state.
- Nothing makes a person from QuickBooks (stage 3's slice 7a): a test that needs a guardian writes the person, the sign-in account and the guardian row (`seedParent()`, `seedGuardian()` in `tests/helpers/db.ts`; FZN's Ana Rivera, `seedAnaRivera()` in `tests/helpers/roster-writes.ts`, after `connectRoster()`). `seedGuardian()` gives the row its family record and its own link itself, as staff's add does, and runs no import (stage 3's slice 12b1; the import touches no guardian row): it writes `family_id`, and the row holds no copy of a customer (migration 0049 dropped them). Given `familyId`, that; `familyId: null` is refused with a `throw` that names the check, but for a `company_changed` row, as the database refuses a row in no family otherwise (`guardian_family_unless_company_changed`): a row that doesn't count is seeded in an inactive family record linked to nothing (`seedInactiveFamily()`), or as a `company_changed` one; given `familyQboId` while the roster names a company, the record that customer's family link names (`recordOfCustomer()`, which makes an inactive one with its link for a customer the import hasn't made yet, made active by the next import once the cache holds it as a family); while the roster names none, one active family record with no link per `familyQboId`, shared by its rows (remembered, and made again after `resetDb()`). That record does not survive an import run while the roster names no company: `syncAppRecords()` (and `seedShape()`, `addToCache()` or `seedRosterRead()` with no realm, which run it) makes every family record it finds no link for inactive, so the gate then refuses the row's person and `whatAFreshRunWouldChange()` is not `NO_CHANGES`; seed such rows after the last import, or seed a roster company first. A row a change of company closed (`company_changed`) is in no family. With a roster company, a `sourceQboId` other than the family's customer gives the row its `carried_over` link to that record, with the cache's version of it when the cache holds it. So seed the roster company and the cache first, then the guardian: a row seeded before the company is in an unlinked record, and stays there when an import makes the linked one. `seedGuardianInFamily()` is the same function, kept by its name for the tests of the door.
- Signed-in parent, vitest: `seedSignedInParent()` and `seedTwoFamilies()` in `tests/helpers/parent.ts` (also `seedParentIn()` for a family the test put in the cache itself, and `identityNow()` after changing a link). Each imports the cache's families and students and seeds the row in its family's record (`seedGuardian()`) before it resolves the session, as the gate lets a parent in only through an active family record, and returns an identity that carries `familyId` (`markersOf()` keeps the QuickBooks ids as markers); a test that builds a ctx by hand takes it from the seeded identity or `recordOfCustomer()`. A test of the door that seeds people by hand with no roster company seeds each row with `seedGuardianInFamily()` (`seedGuardian()`: an active family record with no link, shared by the rows of one `familyQboId`), and a row the gate must not count in an inactive family record (`seedInactiveFamily()`). The parent door is closed unless parent sign-ins are on (`parentDoorClosed()`, stage 3's slice 7b): the parent seeds switch them on (`SIGNINS_ON`, `tests/helpers/roster-cache.ts`), and so does `scripts/seed-e2e.ts`; a test that signs people in by hand switches them on itself (`seedParentSettings(SIGNINS_ON)`), and a test of the closed door switches them off, or deletes the setting for "never switched on". Then import `tests/helpers/signed-in.ts` before anything from `src/` and call `asParent(identity)` (also `asParentChoosing`, `asParentEnrolling` (since the sign-in release's slice SI-10a: the gate's `enrol`, Strict's enrolment; the test marks the session's `enrol_until` itself, `seedParentSession(..., { enrolUntil })`, for the presses that read it again), `asRefusedParent`, `asStaff`, `asRefusedStaff`, `renderPage`, `pageOutcome`, `redirectOf`, `revalidatedPaths`). Example: `tests/integration/parent-helpers.test.ts`. When a helper lacks something, add it there with a small change; do not write a private mock block in a test file.
- A session or an email change seeded by hand: `seedParentSession(authUserId, { familyQboId })` and `seedEmailChange({ familyQboId, ... })` (`tests/helpers/db.ts`, `tests/helpers/email-change.ts`) take the family's QuickBooks id as before and store the app's family (`familyOfSession()`: the family record that id stands for, its link's or the one `seedGuardian()` made for it with no company, the one the person has a row in first; else, with a roster company, `recordOfCustomer()`; it throws with neither), or take `familyId` itself. A session with a recent proof (the sign-in release's slice SI-5a: a change of password or sign-in email needs one): `seedParentSession(authUserId, { strongAt })`, or `proveRecently(identity)` (`tests/helpers/parent.ts`), which gives the person a password (`PROVEN_PASSWORD`) when they have none, dates it a second before the proof by the test's clock, and stamps the session's `strong_at` (now, or the time given: 11 minutes back for one past the window); every test that asks for an email change calls it, and the browser specs that ask stamp the seeded session `now() - interval '5 seconds'` and put it back. A session made on a remembered device (slice SI-5b): `seedParentSession(authUserId, { deviceId })` with a device from `seedDevice()` (`tests/helpers/signin-links.ts`, which takes `createdAt`, `lastUsedAt` and `expiresAt`), or set `device_id` on a seeded session; with none, a session names no device, as one from before SI-5b.
- The real session read (sign-in, renewal, the cookie): import `tests/helpers/page-request.ts` instead and call `fromBrowser(cookie)`. It replaces `next/headers` only, and cannot be imported into the same test file as `signed-in.ts`. Example: `tests/integration/parent-door.test.ts`.
- Money in tests: `seedTwoFamilies()` stores fresh figures for both families (`seedFamilyMoney()`, `moneyMarkers()`; it takes the family by QuickBooks id and stores the row by its app record, `recordOfCustomer()`, as `moneyRow()`, `familyRecordOf()` and `ageMoney()` in `tests/helpers/money.ts` read it back by customer); their ids are not digits, so nothing is ever asked of QuickBooks for them. To read through the stub, use the families in `tests/helpers/money.ts` (`RIVERA`, `CHENOWETH`, with `connectCompany(stub)`, `stubInvoice()`, `ageMoney()`, `setFreshSeconds()`); `stub.oddInvoiceAnswer` makes the stub answer an invoice query with a 200 of any shape. A stored invoice must name a customer of its family (`customerQboId`), in `seedFamilyMoney()` and in `scripts/seed-e2e.ts`, or the row is not shown. A test file that renders a page showing money with QuickBooks connected mocks `@/lib/quickbooks/endpoints` onto the stub (top of `tests/integration/payments-page.test.ts`), so a read can never reach Intuit. `seedRosterRead()` (`tests/helpers/roster-cache.ts`) records a finished refresh and the company it read. A page test that depends on the due words sets the club's zone (The club's date, `docs/agents/operations.md`); the fixtures' due dates are fixed, so never assert "soon" or "late" for them against the real clock.
- A parent's contact edits in tests: `tests/helpers/contact.ts` (`seedContactFamilies(stub)`, `contactForm()` with a version that names whose details it carries, `p:<n>` or `f:<n>`, `personDetails()`, `familyDetails()`, `setPersonDetails()`, `setFamilyDetails()`, `NO_DETAILS`), with the money families, whose ids are digits; since stage 3's slice 11a they save the portal's own rows and send nothing at the save, which `stub.apiCalls()` proves, and since slice 11b the save queues each change for the worker, whose sends `tests/integration/contact-sent-on.test.ts` reads through the stub (with `connectRoster()`, `seedAnaRivera()` and `runWriteQueue()`). The stub answers the customer update (`customersOf()`, `shownTo()`, `inQuickBooks()`) as QuickBooks is understood to, for those sends and the check of the portal's requests, and has switches for a refusal (`updateFault`), an edit made in QuickBooks at that moment (`beforeUpdate`), an answer that is lost (`loseUpdateAnswer`) and a server that can't be reached (`dropApi`). It answers the email update (for the check of the portal's requests, and since stage 3's slice S11e for the worker's sends of a changed sign-in email, which `tests/integration/email-sent-on.test.ts` reads through the stub, confirming with a seeded session and request, `seedParentSession()` and `seedEmailChange()` from `tests/helpers/email-change.ts`; the confirm itself sends nothing) and the staff roster writes the same way (and a duplicate name); `tests/helpers/roster-writes.ts` (`connectRoster()`, `asOp()`, `staffWith()`, `seedQueued()`) sets those up. `stub.oddRosterAnswer` answers the roster's queries with a 200 of any shape; `stub.items` and `stub.oddItemAnswer` do the same for the item list.
- A student moved in a test: `moveInCache()` and `moveFamilyInCache()` (`tests/helpers/roster-cache.ts`) change the cache and the app's records (by the import), so the student is in the other family in the app, as a move staff make leaves them; `moveInQuickBooksOnly()` changes the cache alone, as a move made in QuickBooks leaves it since stage 3's slice 9c. A test that changes `qbo_customer` by hand and then reads a season calls `syncAppRecords()` itself.
- An unlink in a test (stage 4's slice M3b; `unlinkThroughThePress()`, `linkAsConfirmed()` and `relinkFamily()` in `tests/helpers/links.ts`): seed everything first and unlink after, since any helper that runs `syncAppRecords()` (`addToCache()`, `seedCache()`, `seedShape()`, `seedRosterRead()`, `seedSignedInParent()`, `seedParentIn()`, `seedTwoFamilies()`, `connectCompany()`, `connectRoster()`, `studentRecord()` for a customer with no link) runs the whole import, which makes a second family, carried over, for the old customer; a customer that should have no family is written to `qbo_customer` by hand with no import after it.
- Contact details in tests: `seedSignedInParent()` puts the spec's phone on the person's row (at version 0), and `seedTwoFamilies()` gives each person a mailing address there too (`PERSON_ADDRESS` in `tests/helpers/parent.ts`, its strings among the markers); `personDetails()`, `familyDetails()`, `setPersonDetails()`, `setFamilyDetails()` and `NO_DETAILS` in `tests/helpers/contact.ts` read and set them; in the browser run Zelda's are `E2E_DETAILS` (`tests/e2e/details-seed.ts`), which `tests/e2e/family-details.spec.ts` changes and puts back.
- Seasons in tests: `seedSeason()` and `seedTwoFamilySeason()` in `tests/helpers/season.ts`; they take families and students by QuickBooks id and store the app's records (`subjectColumns()`), so a test that names anyone seeds a roster company first (`seedSignedInParent()` does). A test that writes a season row itself uses `subjectColumns()` or `recordOfCustomer()` (`tests/helpers/app-records.ts`); the staff season actions take `String(await recordOfCustomer(qboId, kind))`. `seedTwoFamilies()` seeds a current season for both families, so Home for them has a ruler before `main` and requirement lines in the students box. It also gives each family a payment requirement (the trip deposit: paid for A, open for B), forms with a request in every state and kept evidence for the complete one (`seedTwoFamilyForms()`), a place on one shared volunteer shift with A's student checked in and B credited outside the portal with a staff note (`seedTwoFamilyVolunteering()`), a volunteer buy-out each (A's invoiced as 9174, B's paid as 9285: `seedTwoFamilyBuyouts()` in `tests/helpers/buyouts.ts`, whose `seedBuyout()` takes families and students by QuickBooks id and stores the app's records, `familyRecord()` and `studentRecord()`, and whose `buyoutsOf()` reads them back beside the customers their links name, `buyoutCustomers()`), and a pending email change for each parent (`seedTwoFamilyEmailChanges()`), each with its markers.
- Signed-in parent, Playwright: `await context.addCookies([parentSessionCookie()])` from `tests/e2e/parent-session.ts` (Zelda, family `E2E-FAMILY`, seeded by `scripts/seed-e2e.ts`); staff: `staffSessionCookie()`. A spec that tests the door signs Zelda in by her seeded password (`E2E_SIGNIN.password`, `tests/e2e/signin-seed.ts`) and the code read from the mail sink (`codeFor()`), or by the password alone with her seeded device's cookie (`zeldaDeviceCookie()`), clears `signin_code` and `rate_limit_event` before it starts (5 password tries per address in 15 minutes are fewer than a run's sign-ins of Zelda), and removes the sessions and devices it made. Since the sign-in release's slice SI-8 a sign-in that proved a second step on a new browser (the emailed code, the app's code, a set-up link) lands on Home with the passkey offer: once Home has loaded, call `passOffer(page)` (`tests/e2e/journey-helpers.ts`, which presses "Not now" only when Home drew the box, waiting for the box to read the browser, never a guessed time), and after the spec `resetPasskeyOffer(sql)` (`tests/e2e/signin-links.ts`: Zelda's count of "Not now" back to 0 and her seeded device's stamp off; the devices the spec made go with `removeZeldaDevicesMadeHere()`). A spec that needs the offer drawn makes a session of Zelda's own, made and proved five seconds back on a device of its own (`parent-a11y.spec.ts`'s `offerSession()`, keyboard journey 13): the seeded session is made a day before the run and is never offered it. The seed is at Standard: a spec that needs Strict (since SI-10a: `strict-enrolment.spec.ts`, `parent-a11y.spec.ts`'s `/one-more-step` targets, keyboard journey 14) stores it at its start and puts Standard back after (`storeLevel()`, `tests/e2e/strict-seed.ts`), and never uses Zelda, whose seeded session the gate signs out at Strict (she has no second factor): it makes a guardian of its own in `E2E-FAMILY` with a password and no factor (`makeStrictParent()`) and removes her after with all she made (`removeStrictParent()`).
- Signing a parent in through the door, vitest (since SI-3b): `signInThroughDoor(outbox, email)` from `tests/helpers/parent-door.ts` posts the password (giving the person `DOOR_PASSWORD` when they have none), reads the code from the file's own outbox and posts it with the pending step's cookie; a test of the code functions alone builds the pending step's person with `stepPersonFor()`.
- Fake QuickBooks with `startQboStub()` from `tests/helpers/qbo-stub.ts` and `vi.mock("@/lib/quickbooks/endpoints", ...)` (top of `tests/integration/roster-pages.test.ts`). Fake mail with `vi.mock("@/lib/mail/senders", ...)` and an outbox (`tests/integration/parent-door.test.ts`), or the real SMTP sink in `tests/helpers/mail-sink.ts`.
- A passkey in a test (the sign-in release): `seedPasskey()` stores one as the passkey library does, and `assertionFor()` (`tests/helpers/passkey-keys.ts`) signs with it; since SI-7b a test adds one as a parent does, through the library's registration options and the portal's `/portal-passkey/add` (`addPasskey()` in `tests/helpers/passkey.ts`, with `registrationFor()`'s attestation `none` answer), with a real session cookie from a sign-in through the door (`signInThroughDoor()`), and asks again with one at `/portal-passkey/again` (`passkeyAgain()`). In the browser, Playwright's own `context.credentials` (`tests/e2e/passkey-signin.spec.ts`, `passkeys.spec.ts`).
