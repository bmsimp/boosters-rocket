# Sign-in release

What this covers: the sign-in release (passwords, links, devices, the club's level). The rules of `AGENTS.md` still apply.

## Sign-in release

- The owner approved a new way for parents to sign in: a password chosen from a one-time set-up link, a second step on a new device, passkeys, an authenticator app, a club level of Standard or Strict, and an Admin-only reset; the emailed code stops being a way in by itself. Where its truth lives: `docs/superpowers/specs/2026-11-18-app-owned-families-design.md`, section 6 under "Signing in", the "Sign-in" entry of section 9, open questions 20 to 36 and Appendix A under "Signing in". It is built as its own slices, SI-1 to SI-11 (the roadmap says which have shipped), beside stage 3. Until a slice ships, the rest of this file describes the sign-in as it is (the emailed code alone); the slice that changes it changes the rule in the same commit.
- The lead's decisions for the whole release. The portal owns the password and everything but the passkey ceremony: Better Auth's `emailAndPassword` stays off on the parent side and no two-factor plugin is added; a password is hashed and checked with `hashPassword` and `verifyPassword` from `better-auth/crypto` and kept as the `credential` row of `parent_auth_account`; set-up and reset links, remembered devices, the second step and the authenticator app are the portal's own tables and code over `node:crypto`, so every such write shares the portal's transaction with its audit row. Only WebAuthn (a later slice) is the library's. Set-up and reset links are rows of `parent_signin_token`, hashed with a keyed HMAC as a sign-in code is (`src/lib/parents/signin-codes.ts`), never Better Auth's verification table; remembered devices are rows of `parent_device`, with a last-used time, renewed by use; `signin_code` stays for the second step alone. Nothing of the release is reachable until a later slice links to it.
- What exists so far (SI-1, groundwork; nothing anyone meets changes). The club's level: `ParentSettings.level` (`src/lib/parents/settings.ts`), `"standard"` or `"strict"`, read as Standard when a stored value has none (every value stored before it), in the defaults and in the closed state; a level that is neither word fails the parse and closes the door. Nothing writes it and no page names it; every switch keeps the level stored (`change()` in `switches.ts`), and each `settings.parents.save` audit row's before and after carry it as stored, so the Admin's audit page and its export show `"level":"standard"` in that row's JSON. A save that follows a stored value that failed to parse stores the closed state, at Standard, and a build from before SI-1 drops the level on any save: harmless while nothing stores Strict, and SI-10, which first stores it, keeps a readable level through such a save (or refuses it) and says in `docs/runbooks/updates.md` that going back to a build before SI-1 loses Strict. The tables (empty as SI-1 made them): `parent_signin_token` (purpose `setup` or `reset`, the person, the keyed hash, made, expires, used; one unused per person and purpose, an expired unused one included until the clean-up deletes it, so making a link first deletes or spends the person's unused link of that purpose, expired or not, under the person's lock, as a new sign-in code replaces the old one) and `parent_device` (the person, the keyed hash, made, last used, expires), each going with the person and expired by the daily clean-up; `parent_auth_session.strong_at`, nullable, when the session last proved the password and the second step, which is not a Better Auth additional field (the drizzle adapter writes and returns only the fields its own schema knows, so the library leaves it null and `/get-session` never answers it). Since SI-2 links are made (nothing makes a device yet), and `blockPerson()`, `setSignins(false)`, a confirmed change of sign-in email (`confirmMyEmailChange()`) and closing a person's last open membership (`closeMembership()`; the lead's choice 10), which end all of a person's sign-in, delete every unused link and every device, in the lock order above `lockedPerson()` (`src/lib/parents/sessions.ts`), and count them in their audit rows (`linksDeleted`, `devicesForgotten`); passwords stay. A change of company touches none of it (since stage 4's slice M7a, when `clearParentAccess()` went). Two pure modules, called by nothing in SI-1 and by the link's form since SI-2: the password rule (`checkPasswordRule()`, `src/lib/parents/password-rule.ts`: 12 to 128 characters by Unicode code point, so a combined emoji or a decomposed accent counts as its parts, any characters, a code to turn into words) and the breach check (`checkBreach()`, `src/lib/parents/breach-check.ts`: only the first five characters of the SHA-1 hash go to the Pwned Passwords range service, with the padding header, at the address in `breach-endpoints.ts` that a test points at a stub; found, not found, or not checked, which the spec takes as a password accepted with an audit row saying so; it never throws and logs nothing of the password, its hash or the suffix).
- What SI-2 made (set-up and reset links set a password; nothing links to them, nothing mails a token, nobody is signed in by them). `src/lib/parents/signin-links.ts` (server only): `mintSigninLink(tx, ...)` takes the person's row FOR UPDATE in the caller's transaction, deletes their unused link of that purpose (expired or not), stores the new one and returns its token (32 random bytes, base64url, 43 characters), audited `parent.password.link_made` with the purpose, the expiry and how many it replaced, never the token; nothing in `src/` calls it yet (SI-3a, SI-4 and SI-9 will). Only `hashLinkToken()` is stored: an HMAC-SHA256 keyed with `BETTER_AUTH_SECRET` over `signin-link:<purpose>:<token>`, so a set-up token is never found as a reset token. Set-up links live 7 days (`LINK_LIFE_MS`; open question 34) and work only while the person has no `credential` row; reset links live an hour. `linkVerdict()` is the one decision whether a link may be used (live, its person has a sign-in account, isn't blocked and has a row that counts, and the door is open), writing nothing and making the same reads for every refusal; a token of another shape is no link, answered without a query. The pages `/sign-in/set-up/[token]` and `/sign-in/reset/[token]` (`src/app/sign-in/password-link-page.tsx`) show the form or one message (`PASSWORD_COPY`, `src/lib/parents/password-copy.ts`), and their action (`choosePasswordAction`, a `beforeSignInAction`) calls `choosePasswordFromLink()` (`src/lib/parents/password-set.ts`): the arguments, the limits (`password_link_ip` 60 and `password_link_token` 10 per 15 minutes), the verdict, the two passwords and the rule, the breach check (found is refused in words; not checked is taken, `breachChecked: false` with its code), `hashPassword()` from `better-auth/crypto`, then one transaction under the person's lock that checks the link again, for a reset deletes the unused codes and those spent within a code's life (`CODE_TTL_MS`: the code door's last check, `signinStands()` in `signin-codes.ts`, reads the code its sign-in spent again under the person's lock and refuses, `signin.refused` `code_gone`, when a reset has deleted it, so a sign-in whose code was spent before a reset and whose session is made after it is refused; the daily clean-up keeps a spent code until a code's life has passed since it was spent, so it never causes that refusal), spends the link, replaces or inserts the one `credential` row of `parent_auth_account` (as Better Auth's sign-up writes it), and for a reset forgets every device and ends every session (open question 23), audited `parent.password.set`; every refusal from the limits on is `parent.password.refused` with its reason. Each ask of the breach service leaves a counts-only mark (`markBreachCheck()`, `src/lib/parents/breach-mark.ts`) for the Health page's `breach_check` line. Better Auth's own password routes stay shut with a password present (`emailAndPassword` off, `PARENT_DISABLED_PATHS`; the portal never writes a reset row in the library's verification table; `tests/integration/parent-door.test.ts`). Tests: `tests/integration/password-links.test.ts` and `tests/helpers/signin-links.ts` (`mintLink()`, `seedPassword()`, `seedDevice()`, `seedCode()`), and in the browser `tests/e2e/password-links.spec.ts` with `tests/e2e/signin-links.ts` (a link for Zelda by the same keyed hash, removed after with any password it set).
