# Sign-in release

What this covers: the sign-in release (the one finish, passwords, links, devices, the second step (emailed code, authenticator app, passkeys), Sign-in settings, the club's level). The rules of `AGENTS.md` still apply.

## Sign-in release

- The owner approved a new way for parents to sign in: a password chosen from a one-time set-up link, a second step on a new device, passkeys, an authenticator app, a club level of Standard or Strict, and an Admin-only reset; the emailed code is no way in by itself. Where its truth lives: `docs/superpowers/specs/2026-11-18-app-owned-families-design.md`, section 6 under "Signing in", the "Sign-in" entry of section 9, open questions 20 to 36 (each settled as the spec recommends), Appendix A under "Signing in" (the library notes, the new tables, the tripwires and the sign-in rows of "Audit actions") and Appendix C under "Signing in". The roadmap's sign-in table says what each slice built. A change to any rule below changes this file in the same commit.
- How a parent signs in, in one breath: a password, and on a device the portal doesn't remember a second step: their passkey, their authenticator app's code or a backup code when they hold one, else (Standard only) a code emailed to them; a passkey also signs in alone, with no address typed. Under Strict a guardian with neither a passkey nor an app is led, after their password, only to `/one-more-step` to add one. Staff sign in with Microsoft or Google, unchanged.
- The lead's decisions for the whole release. The portal owns the password and everything but the passkey ceremony: Better Auth's `emailAndPassword` stays off on the parent side and no two-factor plugin is added; a password is hashed and checked with `hashPassword` and `verifyPassword` from `better-auth/crypto` and kept as the `credential` row of `parent_auth_account`; set-up and reset links (`parent_signin_token`), remembered devices (`parent_device`), the second step (`signin_code` for the emailed code), the authenticator app and backup codes are the portal's own tables and code over `node:crypto`, so every such write shares the portal's transaction with its audit row, or is named in `NOT_AUDITED` with why. Links are hashed with a keyed HMAC as a sign-in code is (`src/lib/parents/signin-codes.ts`), never Better Auth's verification table. Only WebAuthn is the library's: `@better-auth/passkey`, the release's one new dependency, pinned to exactly the installed `better-auth`'s version (its peers ask for it); the session its own sign-in would make is refused by the parent instance's guard, and every sign-in of every kind ends in the one finish. The release goes into `main` as a whole: merged into main on the owner's word of 2026-11-21; deploying it waits for stage 3's deploy and the owner's real-device checks.

### What still waits

- Nothing of the release's slices waits now. Three gaps left on purpose, each said where it lives below: a passkey row the library inserted whose recording transaction never committed is not swept (Passkeys), though the removal of passkeys from an earlier address takes it, its origin being null; a reset's link whose mail failed counts as a link emailed earlier to the welcome (The staff reset); and that removal, pressed in the moment between the library's insert of a new passkey and the add's record of its origin, takes the new one too (The staff reset).

## The club's settings and level

- `ParentSettings` (`src/lib/parents/settings.ts`): `signin`, `welcome`, `requireActiveStudents` and `ParentSettings.level`, `"standard"` or `"strict"`, read as Standard when a stored value has none (`DEFAULT_PARENT_SETTINGS`, and `CLOSED_PARENT_SETTINGS`, the closed state); a level that is neither word fails the parse and closes the door. `parseParentSettings()` answers the closed state for every reader of a value that fails to parse. `storedLevel(value)` (pure: a plain object's `level` when it is one of the two words, Standard for a plain object with no `level`, else null) and `readStoredSettings(tx?)` (`{ settings, level }`) give the level stored even then.
- Every switch goes through `change()` (`src/lib/parents/switches.ts`): the parents' settings lock (`pg_advisory_xact_lock` on `PARENTS_KEY`), `readStoredSettings()`, `putParentSettings()`, the work, and one `settings.parents.save` row with `before` and `after` (the Admin's audit page and its export show `"level":"standard"` in that row's JSON). A patch that changes nothing records nothing. A stored value that fails to parse but names a readable level keeps it through any switch (the closed state's other switches with that level); one that names none refuses every patch with no `level` (`LEVEL_UNREADABLE`), and `setLevel()` then stores the closed state's switches with the level chosen, its row's `before` saying `level: null`. `change()` returns what its work recorded (`SwitchResult`'s `did`) and the stored `signin` as it read it under its lock; the other switches drop both (`answered()`). A build from before the release would drop the level on any save; going back to one is a restore of a backup that holds no level (`docs/runbooks/updates.md`, "Going back").
- `setSignins(false)` ends all of everyone's sign-in: welcome emails off, owed welcomes cleared, every unused code, unused or held link, device and session gone, in the lock order above `lockedPerson()`; passwords, apps, backup codes and passkeys stay. On needs working mail (`missingForSignins()`). `setWelcome()` and `setRequireStudents()` as their comments say.
- The count: `factorCounts(tx?)` (`FactorCounts = { people, passkey, app, neither }`), over exactly the people `signinCounts()` counts (not blocked, a row that counts by the students rule in force), in one query with two `exists`: a passkey by `hasPasskey()`'s condition (a `parent_auth_passkey` row of their sign-in account, readable or not), an app by `hasAuthenticator()`'s (`confirmed_at` set); someone with both is in `passkey` and `app`. With sign-ins off they are of who could sign in once sign-ins are on.
- The switch: `setLevel(level, shownNeither, o)` through `change()`, `LevelResult = { ok: true; signedOut; signinOn } | { ok: false; errors }` (`signinOn`: the stored `signin` as `change()` read it under its lock, never a key of the audit row). To Strict from Standard (or from a level that can't be read): `factorCounts(tx)` under the lock, refused with nothing stored and no row when its `neither` isn't `shownNeither` (`LEVEL_COUNT_CHANGED`); then, in the same transaction, in the order of `setSignins(false)`: the rows of every person with a session, in id order (`lockPeople()`), `factorCounts(tx)` again, the sessions of everyone counted as `neither` deleted (open question 21 (a)), and `strong_at` cleared on every other session that has one, so no proof made under Standard is a proof under Strict; devices, passwords, apps, backup codes and passkeys stay; nobody is mailed; the row's `after` holds the stored switches and `{ counts, signedOut, sessionsEnded, proofsCleared }`. Strict may be chosen with sign-ins on or off; with them off nobody can be signed in (the gate ends any session at its next request while the door is closed, `resolveParentSession()` and `parentDoorClosed()`), though a session left from a value never stored or one that can't be read is still deleted and counted in `signedOut`. Removing a factor and starting an app's set-up hold the settings lock shared; confirming an app and recording a passkey don't (they hold the person's row FOR UPDATE, which `lockPeople()` waits for or makes wait), nor does the library's insert of a passkey's row, so the counts recorded are the ones read after `lockPeople()`; a session the switch misses is ended by the gate at its next request, the invariant. Back to Standard (`setLevel("standard", null, o)`): no work, nobody signed out, every factor kept, an enrolling session ended at its next request (`enrol_ended`), remembered devices standing in for the emailed code again. A press for the level stored changes nothing and records nothing.
- The four Strict choices, confirmed by the owner on 2026-11-21, said once: switching back to Standard undoes nothing; no email goes out on the switch (the gate and the enrolment tell each guardian at their next sign-in); a remembered device still asks an app holder for the app's code under Strict (no device stands in for a step there: telling which factor remembered a device would need a column and a proof of it), and Sign-in settings says so; and a stolen password can enrol (until a guardian adds a factor, their password alone reaches `/one-more-step`), a window the switch's confirm and the count on Parents show closing, which nothing narrows.

## The door

### The one finish

- `finishParentSignin()` (`src/lib/auth/parent-signin-finish.ts`, server only) is the only code under `src/` that makes a parent session or sets its cookie. Given Better Auth's endpoint context, the person, the proof of what the sign-in spent (`SigninProof`, `signin-codes.ts`), the visitor's address and the `next` the browser sent, it finds the person's user, makes the session with no family (`familyId: null`) inside its own scope (`whileFinishing()`), asks `signinStands()` (deleting the session when it says no), calls `completeParentSignin()` (no cookie when it answers `sessionEnded`), runs `recordStrongSignin()`, sets the cookie with `PARENT_SESSION_COOKIE_SECONDS` (400 days) and answers `landingPath(next)` or `withReturnPath("/choose-family", next)`; every refusal is one answer, its reason in the checks' `signin.refused` rows.
- The proofs (`SigninProof`): `{ password, codeId }`, `{ password, deviceId }`, `{ link }` (`LinkSigninProof`: the spent link's row, and the `credential` row the set wrote by its id and `updated_at`), `{ password, authenticatorId, signedOutSeen }` and `{ password, backupCodeId, signedOutSeen }` (`SecondFactorProof`), `{ password, passkeyId, signedOutSeen }` and `{ passkeyId, signedOutSeen }` alone (`PasskeyProof`), and `{ password, enrol: true }` (`EnrolmentProof`). `PasswordProof` is the `credential` row's id and `updated_at`; `signedOutSeen` the person's newest "Sign out everywhere" (`parent.sessions.end_all`'s audit row id, `newestSignOutEverywhere()`) as the check read it under the person's row.
- `signinStands()` (`signin-codes.ts`), under the person's lock (`lockedPerson()`): refuses a block, a changed address, a `credential` row no longer the one checked (`password_changed`), and then by kind: a code's proof beside a second factor in force (`second_factor_in_force`) or a code's row gone (`code_gone`; the daily clean-up keeps a spent code until a code's life has passed since it was spent, so it never causes that refusal); a device's row gone, not the person's or expired (`device_gone`); a link's row gone (`link_gone`; the clean-up keeps a spent link for a code's life and takes a link for its expiry only while it is unused) or a password replaced since; the app's row gone, not the person's or not in force (`second_factor_gone`), a backup code's row gone, not the person's or unspent (`backup_code_gone`), a passkey's row gone or not the person's (`passkey_gone`), and for all three a "Sign out everywhere" since the try took its code (`signed_out_everywhere`, as `code_gone` does for the emailed code); for a passkey alone no `credential` row is read (a branch before the password's read: a reset keeps passkeys), its address the one the check read; for an enrolment, that the club is still at Strict (`enrol_not_strict`) and the person still has no factor (`second_factor_in_force`).
- `recordStrongSignin()` (`src/lib/parents/devices.ts`, server only), after `completeParentSignin()` and before the session cookie: one transaction in the order above `lockedPerson()` (the person's row, their devices, their sessions) that reads the person not blocked and the session there (else nothing is written, `signin.refused`, and the finish deletes the session and sets no cookie); for a sign-in that proved the password and a second step (a code's, a set-up link's, the app's, a backup code's, a passkey's, alone or after a password) it remembers the device (`StrongDevice`'s `remember`: a browser whose device cookie names a live device of this same person renews that row, `signin.device_used`, instead of making a copy; otherwise a new `parent_device` row, a new 32-byte token, only `hashDeviceToken()` of it stored, an HMAC keyed with `BETTER_AUTH_SECRET` over `signin-device:<token>`, `DEVICE_LIFE_MS` 90 days, `signin.device_remembered`) and sets the session's `strong_at`; a remembered device's sign-in moves its row's `last_used_at` and `expires_at` on (`signin.device_used`) and leaves `strong_at` as it is (the lead's decision, open question 28's "the password and the second step again": the device stood in for the code, so the sign-in proved only the password at that moment). Every proof records on the session the device it was made on (`parent_auth_session.device_id`). An enrolment skips the strong step (no device remembered, no `strong_at`).
- The cookies: the session's, then the device cookie (`createAuthCookie("device")`, HttpOnly, SameSite=Lax, `Path=/api/auth/parent`, Max-Age the longest browsers allow, `PARENT_SESSION_COOKIE_SECONDS` (400 days), `setDeviceCookie()`; the row is the authority; set again with the same token when a sign-in renews it; one per browser, so a second person on a shared browser replaces it and the first's row stays until it expires), then the pending step cleared. A device token is never stored, logged, audited or sent anywhere but its cookie; one of the wrong shape is no device, answered without a query.
- Who calls it: only the parent code plugin (`src/lib/auth/parent-code-plugin.ts`): `/portal-password/check` (a remembered device's sign-in and an enrolment), `finishSecondStep()` (the code step, the app step and a passkey after a password), `/portal-passkey/check` for a passkey alone, and `finishLinkSignin`, a server-only endpoint (`createAuthEndpoint.serverOnly`: no path, so the router serves it to nobody and `parent-door.test.ts`'s `reachable` list doesn't name it), which a server action reaches through `signInFromLink()` (`src/lib/auth/parent-link-signin.ts`): it calls `finishLinkSignin` by `auth.api` with the request's headers stamped (`stampClientIp()`) and `returnHeaders: true`, and sets each `Set-Cookie` of the answer on `cookies()` with the same name, value and attributes (`cookiesToCopy()`, `src/lib/auth/session-cookie-copy.ts`, pure: `parseSetCookieHeader()` and `toCookieOptions()` from `better-auth/cookies`).
- The guard: the parent instance's `databaseHooks.session.create.before` answers `false` for every session not made inside the finish's scope (`whileFinishing()` and `isFinishing()`, `src/lib/auth/finish-scope.ts`, an `AsyncLocalStorage` that only `finishParentSignin()` enters, around its own `createSession`), so no library route makes a parent session, over HTTP or by `auth.api`, the passkey library's `verify-authentication` included (its `createSession` answers null and it throws `UNABLE_TO_CREATE_SESSION` before any cookie).
- `tests/unit/one-way-in.test.ts` reads every source file under `src/` (comment markers inside a one-line string broken first, so a glob can't hide code) and fails, anywhere but the finish (and, for `setSignedCookie(` and `.setCookie(` alone, the pending step's module, `src/lib/auth/parent-signin-step.ts`, which never names the session's cookie), for `createSession(` (or by name, `["createSession"]`), `setSessionCookie(`, `setSignedCookie(`, `.setCookie(`, a `"set-cookie"` header string, an adapter's `create({ model: "session" })`, an insert into `parent_auth_session` (drizzle's, `schema.` or not, or SQL by name or by `${parentAuthSession}`) or a Better Auth sign-in or sign-up call (`.api.signIn…` or `.api["signIn…"]`); for a caller of the finish but the plugin, a caller of `signInFromLink()` but the link form's action and a name of `finishLinkSignin` but the plugin and `parent-link-signin.ts`; for reading a `Set-Cookie` (`getSetCookie(`, `parseSetCookieHeader(`) anywhere but `parent-link-signin.ts` and `session-cookie-copy.ts`, and for setting a cookie through Next's `cookies()` anywhere but `parent-link-signin.ts` and first-run setup's `src/lib/setup/session.ts`; for a parent Better Auth instance whose `plugins` are not exactly `[parentCodePlugin(), parentPasskeys()]` (a plugin's own routes run in `node_modules`, where the scan can't read); and for a finish whose steps are dropped or reordered or no longer return on a refusal. It reads the spellings it lists, not every way JavaScript could be written. A new way in hands the finish the proof of what it spent, which `signinStands()` reads again under the person's lock.

### The endpoints and the page

- The door is the parent code plugin's endpoints, named off `/sign-in` so the library's own 3-in-10-seconds rule never meets them: `/portal-password/check` (`email` up to 320 characters, `password` up to 1024, `next`), `/portal-code/resend` (no body: the pending step is its guard, always `{ ok: true }`), `/portal-code/check` (`code` up to 20, `next`), `/portal-app/check` (`code` up to 20, `next`), `/portal-passkey/check` (the passkey sign-in, alone or as the step); and for Sign-in settings `/portal-passkey/add` and `/portal-passkey/again`. `rateLimit.customRules` names each: `password_try_ip`'s, `code_send_ip`'s and `code_check_ip`'s maxima in 60-second windows (the code step, the app step, the passkey check, the again and the library's authentication options at `code_check_ip`'s; the add and the registration options at `code_send_ip`'s). The library's paths are in `PARENT_DISABLED_PATHS` but its authentication and registration options (`/passkey/generate-authenticate-options`, `/passkey/generate-register-options`, `PASSKEY_REGISTER_PATH`), each behind the portal plugin's `onRequest`; `/portal-code/send` and `/portal-code/verify` are gone. `tests/integration/parent-door.test.ts` lists every path a parent can reach (`reachable`) and answers 404 for the old ones; Better Auth's own password routes stay shut with a password present (`emailAndPassword` off; the portal never writes a reset row in the library's verification table).
- `/sign-in` draws `PasswordSignIn` (`src/app/sign-in/password-sign-in.tsx`): the email (`autocomplete="username"`) and the password (`current-password`) with one button, **Sign in with a passkey** (`PASSKEY_BUTTON`) after the form with `PASSKEY_EXPLAINED`, and a link to `/sign-in/password` ("Set up or reset my password", while the page is ready); `SIGNIN_LEDE`, drawn before anyone is known, says only that a new device asks for one more thing, never what it is. Then the step the answer names: the code step (`one-time-code`, Resend code, Start again; `CODE_SENT` once the code is emailed), the app step (one field, `APP_CODE_LABEL`, `autocomplete="one-time-code"`, a backup code accepted, Confirm and Start again, no Resend, `APP_ASKED`, its refusal `APP_REJECTED`, its time over `APP_STEP_ENDED`, which promises no new code, posting to `/portal-app/check`) or the passkey step (below). The words are `src/lib/parents/signin-copy.ts`. The device keeps only when the step was asked for, which step (`CodeStep.kind`, `code`, `app` or `passkey` with its `app` bit and `backup`, read only as `true`; read as untrusted, anything else, an older build's value included, the code step) and where to go (`code-step.ts`, no address), so a reload draws the same step; the page keeps the step's first time through a resend, offers no resend in its last minute, and goes back to the password step when its time is over (`CODE_STEP_ENDED`). An ended step (`ended: true` beside `error: "rejected"`, on every refusal that ends it, so it never says why) goes back to the password step with `APP_REJECTED` and `APP_STEP_OVER` (`FACTOR_REJECTED_ENDED`).

### The password check

- `checkPasswordSignin()` (`src/lib/parents/password-signin.ts`, server only), in order: the arguments' types and sizes (anything else refused, uncounted); `password_try_ip` (180 per 15 minutes, skipped with no address); the address through `normalizeEmail()` and the try's place, taken before the person or the password is read, so tries sent at once can't slip past (`takeRateLimitPlace()`, `rate-limit.ts`): on a device the portal remembers for the person the address names (a device cookie of the token's shape naming an unexpired `parent_device` row of theirs, `deviceOfAddress()`, read only when such a cookie is there) under `password_try_device` keyed by the device's row, and otherwise under `password_try_email` (counted under `hashTriedAddress()`, an HMAC keyed with `BETTER_AUTH_SECRET` over `password-try:<address>`, never the address), each 5 per 15 minutes and not taken while the IP is over. A right password that goes on gives its place back (`giveBackRateLimit()`), so only wrong and refused tries count (open question 27's "5 wrong passwords"), a parent's own right password never uses one up, a stranger who keeps an address's count full doesn't keep the parent out on their remembered device, and a passkey (which takes no such place) is the way past it on a new one; nothing clears a count, a reset or a set-up included, since clearing it would tell a stranger keeping it full that the address is a parent's. The third argument is the device cookie's token at the door or `{ deviceId }` from asking again; the last, `TryCount`, a caller's own count the door never passes.
- Then the same reads for every address (the settings, the person with their sign-in account and `credential` row, their rows that count, `hasAuthenticator()`, `hasPasskey()` and `unspentBackupCodes()` (`PasswordCheck.factors`, `{ passkey, app, backup }`), for a fixed nobody when there is none), `verifyPassword()` from `better-auth/crypto` against the row's hash or, with no person or no password, against a dummy hash made once per process (begun when the module loads), outside any transaction, in its turn (`inTurn()`: at most two checks at once in the process, since one is 32 MiB and a tenth of a second or so on Node's four-thread pool, and at most `MOST_WAITING_TO_CHECK` (20) waiting; a try that finds the wait full is turned away at once with the over-limit answer, before it is counted or reads anything, audited `rate_limited` with `limit: "busy"` once per 15 minutes in the process, and one that finds it full at its turn gives its place back; a request whose client has gone, by the request's signal, leaves the wait and runs no check). What follows a right password (the pending step's end, the code's life and `created_at`, the resend wait, the mail's minutes, the device's expiry check) is timed from when the check finished (`PasswordCheck.at`).
- The verdict's reasons in order: `rate_limited` (with `limit`), `not_an_address`, `signins_off`, `unknown_email`, `no_sign_in_account`, `no_password`, `wrong_password` (audited `signin.password_wrong`), `blocked`, `no_enabled_guardian`, each audited `signin.password_refused` once in its own write (over a limit once per full window, naming nobody; for an address that is nobody's an actor with no id and `label: null` and no target: the typed address is in no row and no count). Every refusal is `{ ok: false, error: "rejected" }` with no cookie, and the page's one sentence (`PASSWORD_REJECTED`) with a link to `/sign-in/password`; over a limit (`ip`, `email`, `device`) or turned away by a full wait (`busy`) it is `{ ok: false, error: "rate_limited" }` and `TOO_MANY_TRIES` with no link (a reset doesn't shorten the wait): the count is taken by what the visitor sent before anything is read, so it is the same for any address (the exception in the before-sign-in checklist of `AGENTS.md`).
- A right password: who is asked which step is `secondStepFor()` (`src/lib/parents/second-step-rule.ts`, pure, imports nothing; open question 24): a second factor of the person's own (a passkey or an app in force) at either level, else Standard the emailed code and Strict none (`PasswordCheck.step`: `emailed_code`, `second_factor` or `enrol`). Under Standard a device the request's cookie names for this person, unexpired, finishes the sign-in at once for anyone (`{ password, deviceId }`, `{ ok: true, next }`); under Strict no remembered device stands in for a step (one of the owner's four Strict choices, under "The club's settings and level"), so a factor holder is asked on every device, and a person with none is answered with Strict's enrolment (`step: "enrol"`, no device, `signin.second_step_asked` with `step: "enrol"`, finished at once with `{ password, enrol: true }`). Otherwise `signin.second_step_asked` is audited and the pending step set: for a passkey holder `{ ok: true, step: "passkey", app }` (and `backup: true` beside it with no app and unspent backup codes, `passkeyStepAnswer()`: never beside `app: true`); for an app holder `{ ok: true, step: "app" }`, no code sent and no `signin_code` row; otherwise the emailed code is sent (below) and the answer is `{ ok: true, step: "code" }` whatever happened to the mail. An unfinished app set-up is no second step. Asking again refuses an `enrol` answer.

### The pending step

- A signed, HttpOnly cookie of the portal's own, never a session or a row, set, read and cleared only by `src/lib/auth/parent-signin-step.ts` (and through it by the finish): `createAuthCookie("signin_step")` (so `br_parent.` plus its name, `__Secure-` and Secure under https, SameSite=Lax), `Path=/api/auth/parent`, its value base64url JSON of the person, the address the password was proved with, the `credential` row's id and `updated_at` and its end (`CODE_TTL_MS` after the right password, never extended), set with `ctx.setSignedCookie()` and read with `ctx.getSignedCookie()`; one unsigned, mis-signed, malformed or past its end is no step. It is made only after a right password, so a stranger who knows an address can never make the portal mail a code; it is cleared by a sign-in that finishes and by a refusal that ends it (the code's fifth wrong try, a block, an address or password changed, sign-ins off, a finish that refuses). `/portal-code/resend`, `/portal-code/check` and `/portal-app/check` take the person and the address from it alone; with none they are refused (`refuseCodeWithoutStep()`: `code_check_ip` counted, `signin.refused` `no_pending_step` naming nobody), so a code alone signs nobody in. Under Strict a pending step made at Standard goes no further: the resend and the code check end it (`strict_no_factor`, `doorStops()`).

### The emailed code

- `sendSecondStepCode()` (`signin-codes.ts`): for the person, never a typed address, with the code's own lock, the address and the password read again under `lockedPerson()`, the resend wait (`RESEND_AFTER_MS`, a minute), `code_send_email` (3 per 15 minutes) under the person's own address, `code_send_ip` (60), the mail after the transaction and not awaited, `signin.code_sent` and `signin.code_refused`. It sends nothing to a second factor's holder (`signin.code_refused` `has_second_factor`, not ended), read before its lock and again under it before a code is stored, and answers `app`, `passkey` and `backup`, so the door and asking again ask for the factor even when it came into force after the password's reads. It answers `ended` when the step can't go on (a block, an address or password change, no row that counts, sign-ins off or Strict landing just then), when no pending step is set. A code never outlives its pending step: the first ends with it, and one resent (`StepPerson.endsAt`) expires at the step's end or `CODE_TTL_MS` (10 minutes) on, whichever is sooner, its mail saying how many whole minutes (`signinCodeMessage()`'s `minutes`), and none is sent with less than `LEAST_CODE_LIFE_MS` (a minute) of the step left (`signin.code_refused` `step_ending`). Its `use` (`CodeUse`, `sign_in` by default; asking again passes `change`) picks the mail: `signinCodeMessage()` (a code comes only after the right password; if the reader didn't just sign in, set a new password from "Set up or reset my password") or `changeCodeMessage()`.
- `verifySigninCode()` takes the step's person and password (`{ parentId, email, password }`), refuses before it looks at the code a person blocked, a `credential` row no longer the one the step proved (a block and a reset delete the codes too) or a second factor in force (`signin.refused` `has_second_factor`, not ended, nothing spent, and the same again after the code is taken for one that came into force meanwhile), keeps its 10 minutes, 5 tries and `code_check_ip` (180), and answers the code's row id and whether the step has ended. `signinStands()` refuses a code's proof while the person has a second factor in force under the lock (`second_factor_in_force`), so a code mailed before the factor, for a pending step made before it in another tab, never gets in. `secondFactorFor()` counts a passkey beside the app for the door and asking again alike, so a holder is never emailed a code anywhere.

### The app step and backup codes at the door
