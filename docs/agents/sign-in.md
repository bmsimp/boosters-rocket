# Sign-in release

What this covers: the sign-in release (passwords, links, devices, the club's level). The rules of `AGENTS.md` still apply.

## Sign-in release

- The owner approved a new way for parents to sign in: a password chosen from a one-time set-up link, a second step on a new device, passkeys, an authenticator app, a club level of Standard or Strict, and an Admin-only reset; the emailed code stops being a way in by itself. Where its truth lives: `docs/superpowers/specs/2026-11-18-app-owned-families-design.md`, section 6 under "Signing in", the "Sign-in" entry of section 9, open questions 20 to 36 and Appendix A under "Signing in". It is built as its own slices, SI-1 to SI-11 (the roadmap says which have shipped), beside stage 3. Until a slice ships, the rest of this file describes the sign-in as it is (what SI-1 to SI-7b below made: since SI-3b a parent signs in with a password and, on a device the portal doesn't remember, the emailed code as the second step; since SI-6a a parent with an authenticator app in force is asked for its code or a backup code there instead, and is never emailed a code; since SI-7a a parent with a passkey signs in with it alone, with no address typed, or is asked for it after their password in place of the emailed code, and since SI-7b adds, names, lists and removes passkeys on Sign-in settings, is asked again with one and is never emailed a code anywhere; since SI-6b a parent sets the app up, sees its backup codes once, makes new ones and turns it off on Sign-in settings; the code alone signs nobody in; since SI-4 the welcome carries the set-up link that chooses a first password; since SI-5a a parent's Sign-in settings page changes the password and signs out everywhere, and a change of password or sign-in email asks again for the password and the code (since SI-6a the app's code or a backup code for an app holder; since SI-7b, for a passkey holder, the passkey alone, or the password and then the passkey or, beside an app, the app's code or a backup code) unless the session proved itself in the last 10 minutes (since SI-6b, with a proof no older than the moment the person's authenticator app came into force, and since SI-7a no older than their newest second factor, a passkey included); since SI-5b that page lists the remembered devices and forgets them, and a device is renewed while a session made on it is used); the slice that changes it changes the rule in the same commit.
- The lead's decisions for the whole release. The portal owns the password and everything but the passkey ceremony: Better Auth's `emailAndPassword` stays off on the parent side and no two-factor plugin is added; a password is hashed and checked with `hashPassword` and `verifyPassword` from `better-auth/crypto` and kept as the `credential` row of `parent_auth_account`; set-up and reset links, remembered devices, the second step and the authenticator app are the portal's own tables and code over `node:crypto`, so every such write shares the portal's transaction with its audit row. Only WebAuthn is the library's (since SI-7a, `@better-auth/passkey`, the release's one new dependency): the session its own sign-in would make is refused by the parent instance's guard, and every passkey sign-in ends in the one finish. Set-up and reset links are rows of `parent_signin_token`, hashed with a keyed HMAC as a sign-in code is (`src/lib/parents/signin-codes.ts`), never Better Auth's verification table; remembered devices are rows of `parent_device`, with a last-used time, renewed by use (since SI-3b at a password sign-in on the device; since SI-5b also while a session made on it is used); `signin_code` stays for the second step alone. SI-1 and SI-2 are reachable by nothing and may merge at any time; SI-3a is the first slice a parent can reach (`/sign-in` links to the request page, which mails links), so it merges only after stage 3 is released (the owner's choice 1). SI-6a's app step is met only by a person with an authenticator app in force, and nothing a parent or staff can press makes one until SI-6b.
