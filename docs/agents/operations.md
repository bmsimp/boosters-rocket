# Operations

What this covers: the club's date, installation and backups, Postgres, the visitor's address, unasked mail, the Health page and the daily clean-up. The rules of `AGENTS.md` still apply.

## The club's date

- `clubToday()` (`src/lib/settings/club.ts`) is the one place that decides which day it is: the date in the club's own time zone (a Club setting, an IANA name, UTC until set). Step ranges, a requirement's due date and an invoice's due words all use it. Never the server's date (`new Date()` cut to a day) or the viewer's for anything a parent reads as due or past.
- A test that needs two different days at one instant sets the club's zone to `Pacific/Kiritimati` and `Pacific/Pago_Pago`, which never share a calendar day (`tests/integration/payments-page.test.ts`, `seasons-parent.test.ts`).

## Operations

- `scripts/backup.sh <folder>` dumps the portal's database and Documenso's (`BR_DOCUMENSO_DB_NAME`; a database named `documenso` when unset), checks each can be read back, keeps both or neither, keeps the newest 14 of each and records the time and whether Documenso's was in it in the setting `backup.last_success` (the Health page's backup line says so). Its usage and its output say that the signing certificate (the `.p12`) with its passphrase and the env file must be kept somewhere safe too. `scripts/restore.sh <file> <database> [--owner <role>]` loads either kind beside the target and renames it in only when all of it loaded; it refuses a target in use, counting every session listed under it that would stop the drop but its own (not an autovacuum worker, which Postgres ends itself on a drop or rename and which runs as no role, `usesysid` null, so a role that can't see its `backend_type` knows it too; a replication or background worker connected to it is counted) and giving one on its way out about two seconds to go, and it looks at the target over one connection, so its own look is never counted.
- A real installation is `deploy/`: `compose.yml` (Postgres 18 with both databases and their own roles, made by `initdb/10-databases.sql`; migrate, app, worker; Documenso v2.22.0 as the verification requires; the nightly `backup` service running `scripts/backup-schedule.sh` at `BACKUP_AT` club time; an optional Caddy proxy behind the `proxy` profile that sets the bare client address), pulling the published image by default; `compose.build.yml` builds it from the checkout instead. Every image is pinned by digest, and every setting a club must choose is `${VAR:?}` with no default. `.github/workflows/release.yml` publishes the checked image to the GitHub Container Registry on a release (its version, the commit's first 12 characters, `stable`), and `.github/dependabot.yml` asks for dependency updates monthly, one pull request per package, image or action, never grouped (`tests/unit/deploy-names-no-host.test.ts` fails on a `groups` key). The runbooks a club volunteer follows are in `docs/runbooks/` (first install, Intuit, mail, Documenso, backups, updates, restore, reconnecting QuickBooks, Health warnings: one entry per line of `healthReport()`), with the owner's checks before the first family in `before-the-first-family.md`; `poc-linuxdev.md` is the record of the proof of concept. `tests/unit/owner-docs.test.ts` fails when that runbook or `README.md` names a file, a page address, a link or a heading that doesn't exist. The image's own `TZ` is UTC; `deploy/` sets the club's zone. `tests/unit/deploy-names-no-host.test.ts` fails on a host name, address, provider or secret written in `deploy/`, the runbooks or the release workflow: a public site a step must name goes in its `SITES` on purpose. `scripts/poc/deploy.sh` backs up before it migrates and stops if that fails. `deploy/`'s migrate service runs `migrate.mjs --backup-check` (`scripts/backup-check.mjs`, plain JavaScript in the image): with migrations applied and more to apply, it refuses unless `backup.last_success` is less than 26 hours old, saying `docker compose run --rm backup --now` and to start again; an empty database or nothing to apply never stops, and `MIGRATE_WITHOUT_RECENT_BACKUP=yes` on the command line lets one start through (never in `.env`; `docs/runbooks/updates.md`). The lead chose the 26 hours; the owner can still change it. `tests/integration/backup-restore.test.ts` really dumps, restores and compares, through the database's container (`BR_TEST_DB_CONTAINER`, default `booster-rocket-db-1`; CI names its Postgres service's container), or the machine's `pg_dump` and `psql` when that container doesn't hold the database. Neither script prints a secret; new scripts join the shellcheck list in `.github/workflows/ci.yml`. CI runs on GitHub-hosted runners: the repository is public, so they are free, and the variable `CI_RUNNER_LABELS` is unset here. `ci/runner/` is a club's own CI runner for a fork or a private repository that sets that variable (its README says how to bring it up): GitHub's runner beside a Docker daemon of its own (`br-ci-dind`), so nothing CI starts sits beside the machine's other containers, and `tests/unit/deploy-names-no-host.test.ts` scans it too. This repository's own runner was stopped and removed from GitHub on 2026-11-23. A self-hosted runner must never serve a public repository (a fork's pull request would run on it). Since CI no longer runs on `main` by itself, a release is preceded by `gh workflow run ci.yml --ref main`, finished green: `release.yml` (which runs where CI does) publishes only a commit CI has passed on.
- Pull request previews (`docs/superpowers/specs/2026-11-27-pr-previews-design.md`; a draft, not yet run on any machine): `scripts/poc/preview.sh up <n>` runs pull request `<n>`'s head at `https://pr-<n>.<preview domain>` with `docker-compose.preview.yml`, a project of its own (`booster-rocket-pr-<n>`) on the e2e seed's data with its own secrets, every service that runs the branch's code on that preview's internal network only (mail goes to its mailpit), behind one shared proxy (`docker-compose.preview-edge.yml`) that answers only what came through the access gate. It refuses a fork's pull request whoever asks, fetches the branch and never `refs/pull/<n>/head`, and `sweep` takes down every preview whose pull request closed. `tests/unit/pr-preview.test.ts` holds those properties.
- Postgres is 18 everywhere (`docker-compose.yml`, `docker-compose.poc.yml`, `deploy/compose.yml` pinned by version and digest, CI's service, `scripts/smoke-image.sh`). The 18 image keeps its data in `/var/lib/postgresql/18/docker`, so each compose file mounts a new volume at `/var/lib/postgresql` and Postgres 16's old volume read only at `/old-data`, and starts the image through `scripts/postgres-guard.sh`: while the old volume holds data that hasn't been moved, a move is unfinished, or Postgres 16 has been used since the move, it refuses to start, changes nothing and names the runbook section (`BR_MOVE_RUNBOOK`). Never mount a data volume another way or start the image without the guard: an empty Postgres 18 beside unmoved data would greet the club with `/setup`. `scripts/move-postgres.sh <deploy|poc|dev> <folder> [--again [--discard-18]] [--leave-others]` is the move: it never writes to the old volume (it copies it through a read-only mount and runs Postgres 16 read only on the copy, refusing while anything else has it open for writing), names any database or role it wouldn't carry before it changes anything, backs up with backup.sh and Postgres 16's tools, loads a fresh 18 with restore.sh and compares every table's row count; it can be cut off and run again, and `--stop` removes what a cut-off move left. `--again` (after going back to 16) first backs up what 18 holds into `<folder>/postgres-18-before-again` and stops, unless told `--discard-18`, when 18 holds audit rows from the move's time on; `tests/integration/postgres-move.test.ts` runs it for real, and `tests/unit/postgres-version.test.ts` holds the places together. `docs/runbooks/updates.md`, "Moving to a new major version of Postgres", is the club's section, and `poc-linuxdev.md` section 8 the proof of concept's. A backup made by 18 can't be loaded into 16. `.github/dependabot.yml` never offers a new major version of postgres: the lead's choice, so a move is always a release of its own.
- A visitor's address is read in one place, `clientIpFrom()` (`src/lib/request.ts`), from the one header named by `CLIENT_IP_HEADER` (`src/env.ts`; default `cf-connecting-ip`, or `none`). Better Auth is never pointed at a header of its own: it reads the portal's stamp, written by `stampClientIp()` and `withClientIp()`. Never copy a Next.js request with `new Request(req)`: build it from its parts, as `withClientIp()` does. With no address (`none`, or a header the proxy doesn't send) the per-IP sign-in limits are skipped, since every visitor would share one count, and with `none` Better Auth is told so (`clientAddress()`, `src/lib/auth/client-address.ts`), so its own caps are skipped too; with a header the proxy doesn't send it is not, and its caps per path (the defaults and `customRules`) fall back to one count per path shared by every visitor, which a stranger can fill (`resolveRateLimitConfig()`'s `no-trusted-ip` key); the Health page's parent line says when the latest sign-ins have no address. Nor can a cap per address hold the passkey library's challenge (`/passkey/generate-authenticate-options`, which writes a `parent_auth_verification` row for every visitor who asks, living 300 seconds): the worker deletes expired rows of that table at every wake (`sweepExpiredChallenges()`, `src/lib/jobs/cleanup.ts`, one delete counted by the database, its count in the mark `worker.mark.challenge_sweep` and the wake's answer only when it removed some; the daily clean-up's delete of them stays), so with no address the table holds about five minutes of requests and one wake. A sweep that throws is marked, and the Health page's clean-up line (no line of its own: it is the clean-up's delete, run more often) says so while that is the mark's latest word (`SWEEP_FAILED`, `src/lib/health/report.ts`); after a failure the next sweep that works marks even when it removed nothing, so the line clears.
- The portal's address is `APP_URL`, set by whoever installs it. No host name is written into code, scripts or env examples: `scripts/poc/setup.sh` takes the address as its argument, and `deploy.sh` refuses an env file without one. The setup page and the Health page show the address and warn when the browser reached the portal under another (`PortalAddress`).
- Mail a family didn't ask for (scheduled form reminders, volunteer due-date nudges, and the payment and checklist due-date reminders of `src/lib/seasons/due-reminders.ts`: 14 and 3 days before, one email per guardian, family and due date, claimed in `requirement_reminder`, a payment's amount only through `paymentStanding()` from fresh figures and nothing at all when it is paid or the figures are missing or over 48 hours old) goes only while parent sign-ins and welcome emails are both switched on, the Admin's sign that the club is ready to email families (so do the welcome and the mail an Admin's press owes to people welcomed before, `sendOwedWelcomes()`, `docs/agents/sign-in.md`), and, with the day-before shift reminder, only to guardians whose row counts at the gate (`guardianRowCounts()`, `src/lib/parents/sessions.ts`), so nobody is asked to sign in where they would be refused; "Remind now" and the day-before shift reminder need parent sign-ins on. A club message's email (`src/lib/messages/mail.ts`, `docs/agents/messages.md`) is gated by the club's own switch instead (Settings, Messages, an Admin's), goes to the sign-in addresses of people whose guardian row counts at the gate, and is sent by the worker a batch at each wake. Scheduled ones go from the first wake on or after 9:00 club time; each is claimed before it is sent, so two wakes never send it twice; each batch is audited with counts, never an address.
- The Health page (`/staff/settings/health`, Admin only) is `healthReport()` in `src/lib/health/report.ts`: one line per part, in words, with when it last worked. It has lines for Documenso (`forms`, with evidence waiting and any hash mismatch), for the daily read of every family's invoices (`money`), the daily buy-out check (`buyout_check`) and the volunteer reminders (`volunteer_reminders`), both read from the counts-only marks the worker writes after each run (`markJob()`, `src/lib/jobs/marks.ts`; built in `src/lib/health/job-lines.ts`), and the payment and checklist reminders (`due_reminders`, the setting `season.due_reminders`), and the password breach check (`breach_check`, after the parent sign-ins line, from the counts-only mark each ask of the service leaves: `markBreachCheck()`, `src/lib/parents/breach-mark.ts`, the setting `health.mark.breach_check`); the parent sign-ins line says when welcome emails are waiting because mail is failing (the welcome mark, `WELCOME_MARK`); the QuickBooks line counts staff writes waiting or stuck, says when a change was last made in QuickBooks (`QUICKBOOKS_WRITE_ACTION`) and how it connects ("through Boosters Rocket" or "with the club's own Intuit app"); Boosters Rocket Connect, the relay, has its own line (`quickbooks_relay`, `quickbooksRelayLine()`, right after it), shown only in relay mode (tokens held through it, or the relay chosen for the next Connect with the portal's key made), with the relay's address, the last renewal through it and when it last answered and failed, read from the counts-only mark every signed call leaves (the registration's check marks only an answer, never a failure; `health.mark.quickbooks_relay`, `RELAY_MARK`, `src/lib/quickbooks/relay.ts`): it never calls the relay on load. A new outside service or job adds its line there, its entry to `docs/runbooks/health-warnings.md`, and its key to `tests/integration/health-page.test.ts` and `tests/e2e/ops.spec.ts`. `/api/health` stays a bare liveness check.
- The daily clean-up (`cleanUp()` in `src/lib/jobs/cleanup.ts`) deletes only rows strictly past their life. A setting whose feature is gone is past its life: a key listed in `RETIRED_SETTINGS` is deleted there (none is listed now: migration 0046 deleted the previous company's snapshot and the review notice's mark; the delete runs only while the list holds a key). Every table is named once in `CLEANED_TABLES` or `KEPT_TABLES` (with why), and `tests/integration/cleanup.test.ts` fails for a table in neither. A new table whose rows expire gets its delete there, with a boundary test (a row one second inside its life stays).
