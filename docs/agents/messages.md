# Club messages

What this covers: messages staff post to every family, their versions, files, read state and mail, the club's email switch and a staff member's contact email. The spec is `docs/superpowers/specs/2026-11-23-club-messages-design.md`, built in the slices of `docs/superpowers/plans/2026-11-23-club-messages.md`; until a slice ships, this document describes what is built. The rules of `AGENTS.md` still apply.

## What is built (slice 1, foundations)

- The tables (migration `0057_club_messages`, `src/lib/db/schema.ts`): `message` (exported as `clubMessage`: `message` is a common local name, an HMAC's input or an action's answer, that `tests/unit/audit-rows.test.ts` would take for the table), `message_version`, `message_file`, `message_version_file`, `message_read`, `message_mail`, and `staff_user.contact_email`. A message row is never deleted: an Admin's delete erases its versions' content and files and stamps `deleted_at` with `deleted_by` (a check holds them together). A version is never changed; `n` is unique per message, from 1, and a title is 1 to 120 characters. A file is held (`held_by`, and `message_id` for an edit or null for a new message) until a post or edit saves it, or posted (`held_by` null, `message_id` set): a check refuses one that is neither. Its `type` is one of `MESSAGE_FILE_TYPES` (`src/lib/messages/file-types.ts`, a short name such as `pdf`, from which the file route builds its MIME type and its fixed name `attachment.<ext>`), at most `MESSAGE_FILE_MAX_BYTES` (10 MB, the check's number too). `message_read` is one row per message and parent, gone with the person; `message_mail` one row per version and address, the address lower-cased and trimmed (a check), staff only. None is keyed by a QuickBooks id: a change of company clears nothing here.
- The daily clean-up (`src/lib/jobs/cleanup.ts`): a held file over `HELD_MESSAGE_FILE_HOURS` (24) that no version lists, and the mail rows of a version saved over `MESSAGE_MAIL_DAYS` (90) ago. The other four tables are kept.
- Permissions (`src/lib/permissions/registry.ts`, words and the area Messages in `words.ts`): `Messages.Post.ReadWrite` (a custom role may hold it: see every message and its mail results, post, edit one's own), and the Admin-only `Messages.Delete.ReadWrite` and `Settings.Messages.ReadWrite`.
- The club's switch (`src/lib/settings/messages.ts`): the setting `messages.email_allowed`, `{ emailAllowed: boolean }`, off until an Admin turns it on; anything stored but `true` reads as off. `setMessagesEmailAllowed()` audits `settings.messages.change` with before and after, and writes nothing when the value is already set. Its Settings item `messages` (group Club) is seen with `Settings.Club.Read` and changed with `Settings.Messages.ReadWrite`; someone who may see it but not change it gets the line "Only an Admin can change this." Its rail status is "Emailing on" or "Emailing off".
- A staff member's contact email (`src/lib/staff/contact-email.ts`, the card on `/staff/account`, `setMyContactEmailAction`, a `staffSelfAction` that takes no id): null means the sign-in address, and an address typed equal to the sign-in address is stored as null, so a later change of sign-in address is followed. Audited `staff.contact_email.change` with the address shown before and after and whether it was the person's own (`own`).
